# 字节 Superpowers 研发流程与实时观察板设计

## 1. 背景与目标

当前字节专属研发 skill 以 OpenSpec 为核心，但尚未正式投入使用。新的字节流程直接采用原生 Superpowers 规格与计划，不再维护字节 OpenSpec 方言；通用的 `cosh-requirement-review-planner` 保持不变。

本次迁移需要同时解决三类问题：

1. 在编码前建立严格、可追溯的技术方案准入评审；
2. 用原生 Superpowers 规格、计划和实施子任务驱动最小范围编码；
3. 用实时观察板展示状态，但所有硬门禁都由后端与自然语言执行流程共同保证，页面不是流程事实源。

新 skill 暂定命名为 `cosh-byted-superpowers-review-planner`。旧的字节 OpenSpec skill、脚本和字节专属测试会迁移并重命名，不在字节目录中保留两套框架。通用 OpenSpec skill 不受影响。

## 2. 设计原则

- **原生 Superpowers**：规格和计划沿用 Superpowers 的原生位置与格式，不复制或改写成另一套 DSL。
- **硬门禁**：前一阶段没有当前版本的有效通过证据，后一阶段在页面、API 和自然语言三条入口都不可执行。
- **失败关闭**：状态缺失、解析失败、证据过期、文档版本不匹配或请求伪造时一律阻塞。
- **最小修改面**：优先复用现有基建；确需修改时优先增加边界清晰的新函数，避免扩大原代码影响范围。
- **事实先行**：评审和计划必须落到具体仓库、文件、符号、变量、接口和调用链，不接受只描述概念的实施方案。
- **可观察但不依赖页面**：观察板读取同一状态模型；不打开页面时，skill 仍可通过自然语言完整执行流程。
- **不使用 Hammer**：字节流程不调用 Hammer，只参考其远程 UT 的能力边界，实际远程测试使用 `bits-remote-ut`。
- **可蒸馏而不自修改**：归档可以产出候选规则，但不得自动修改公共 skill。

## 3. 产物与目录

### 3.1 Superpowers 原生产物

```text
docs/superpowers/specs/YYYY-MM-DD-<work>-design.md
docs/superpowers/plans/YYYY-MM-DD-<work>.md
.superpowers/sdd/<plan>/progress.md
```

这些文件保持 Superpowers 原生语义。观察板只解析并展示，不在其中写入字节专属控制字段。

### 3.2 字节流程旁路状态

```text
.superpowers/byted-work/<work-id>/
├── workflow.json
├── source.json
├── control.json
├── reviews/
│   ├── round-001-stability.json
│   ├── round-001-security.json
│   └── round-001-feasibility.json
└── evidence/
    ├── knowledge-gate.json
    ├── codegraph.json
    ├── remote-ut-task1.json
    ├── cr-task1.json
    └── push.json
```

旁路状态只承载门禁、证据和观察信息，不改变原生规格与计划格式。

### 3.3 本地归档

```text
.superpowers/byted-archive/<work-id>/<completed-at>-retrospective.md
```

`.superpowers/byted-archive/` 必须加入 `.gitignore`。归档只在本地保存，不进入业务提交。

## 4. 开发任务模型

页面与 API 统一使用“开发任务”，不再使用 “Change”。一个开发任务包含一个技术方案、一组评审轮次、一份规格、一份计划和若干实施子任务。

- URL 查询参数使用 `work=<work-id>`；
- API 使用 `/api/works`、`/api/status?work=`、`/events?work=`；
- 多个开发任务可以并存，并通过顶部开发任务选择器切换；
- 每个开发任务有独立页面状态、评审证据、计划进度和归档。

## 5. 强制状态机

主流程如下：

```text
技术文档接收
  → AI-Spec 知识门禁
  → CodeGraph 代码事实扫描
  → 稳定性 / 安全性 / 可行性三路独立评审
  → 评审闭环确认
  → 生成 Superpowers 规格
  → 精确实施定位校验
  → 生成 Superpowers 计划与实施子任务
  → 子任务编码 / 远程 UT / CR / 提交
  → 最终远程 UT
  → 最终代码评审
  → Git push
  → 本地归档
```

每个阶段只有 `pending`、`running`、`blocked`、`passed` 四种状态。阶段通过必须同时满足：

- 证据文件存在且可解析；
- 证据关联当前技术文档版本、规格版本或代码 SHA；
- 所需检查项完整且无未关闭阻塞项；
- 前置阶段仍然有效；
- 状态转换由后端验证器批准。

文件存在不等于通过。隐藏按钮也不等于门禁：后端必须拒绝越级、过期或伪造的推进请求。自然语言执行同样先调用同一验证规则。

## 6. 知识门禁与三路独立评审

### 6.1 AI-Spec 知识门禁

流程自动检测 AI-Spec 是否已接入及版本是否满足要求，并尝试安装或更新。知识门禁记录来源、版本、更新时间和规则摘要。

AI-Spec 暂时不可访问时，可以显式进入“通用规则降级”分支，但该分支不是跳过门禁：

- 必须记录安装或更新失败原因；
- 必须加载版本化的通用稳定性、安全性和可行性规则；
- 观察板明确显示“通用规则降级”，不能伪装成 AI-Spec 已通过；
- 三路独立评审仍然必须执行；
- 恢复 AI-Spec 后，技术文档进入下一主要阶段前必须补做知识门禁与受影响评审。

### 6.2 CodeGraph 代码事实扫描

在三路评审前读取目标仓库并形成事实快照，至少包含：

- 相关文件和模块；
- 入口函数、被调用函数和关键调用链；
- 涉及的变量、类型、接口和配置；
- 当前行为、潜在影响面和可复用基建；
- 事实快照对应的代码 SHA。

评审只能引用可定位的代码事实。观察板评审区域将问题统一称为“风险点”，不称为“修改点”。

### 6.3 三路独立评审

至少启动三路相互独立的评审执行者：

1. 稳定性评审；
2. 安全性评审；
3. 可行性评审。

每一路输出结构化结果：评审阶段、输入技术文档版本、代码 SHA、结论、未通过风险点、证据、影响、建议修改方式和复审范围。任何一路未通过，整体评审状态为 `blocked`。

## 7. 技术文档修改与评审闭环

评审未通过后提供两个选择：

- 不修改技术文档：保持阻塞，展示风险点与修复建议；
- 修改技术文档：进入可选的文档修改流程。

技术文档一旦修改：

1. 生成新版本号、内容哈希、修改摘要和时间；
2. 当前知识门禁、代码事实快照和三路评审结论全部失效；
3. 从 AI-Spec 知识门禁重新开始；
4. 重新执行代码事实扫描和三路完整评审，不能只复审上次未通过的一路；
5. 历史轮次保留，但标记为“旧版本，仅供追溯”。

这个循环允许重复任意轮次。只有当前技术文档版本的三路评审全部通过，才能执行评审闭环确认并生成规格。

## 8. 规格、精确定位与计划

评审闭环确认后，生成 Superpowers 原生设计规格。规格必须覆盖已通过的评审结论、风险控制和非目标范围。

在生成实施计划前再次校验精确修改位置：

- 每个预期改动必须明确文件、符号、变量或接口；
- 明确复用的现有基建；
- 说明为何需要新增函数以及新函数边界；
- 说明不能修改的代码范围；
- 规格与当前代码事实不一致时退回评审阶段。

随后生成 Superpowers 原生实施计划。计划不能包含占位内容，每个实施子任务必须声明目标、允许修改范围、验证方式和完成条件。

## 9. 编码规范

字节实施任务遵循以下通用规范：

- 保持代码简洁，优先复用已有函数、组件、接口和测试基建；
- 没有可复用能力时才新增；
- 需要改变行为时优先增加边界清晰的新函数，减少对原函数的侵入；
- 不做与当前实施子任务无关的重构；
- 新增或修改的关键逻辑需要中文注释，注释说明原因、边界或约束，不逐行翻译代码；
- 关键状态变化、异常和外部调用提供可观测日志；
- 日志不得泄露密钥、隐私数据或完整敏感请求。

## 10. 实施子任务推进模式

任务页顶部提供两种模式切换：

### 10.1 逐一任务校验

这是严格串行模式：

1. 锁定当前 `Task N` 的文件、符号、变量和接口范围；
2. 只开发当前子任务，后续子任务保持锁定；
3. 实际修改超出计划范围时立即阻塞，要求回退或更新计划并重新通过相应门禁；
4. 编码完成后使用 `bits-remote-ut` 执行当前子任务的远程 UT，不运行本地业务 UT；
5. 远程 UT 通过后执行当前子任务 CR；
6. CR 未通过时只允许修复当前子任务，然后重新执行远程 UT 与 CR；
7. CR 通过后，当前任务右上角才显示并启用“推进下一个任务”；
8. 推进时校验暂存区，提交当前任务范围内尚未提交的文件；
9. 提交成功并记录 commit SHA 后关闭当前范围，解锁 `Task N+1`。

无关文件进入暂存区时阻止推进。界面按钮、API 和自然语言均不能并行开发后续任务。

### 10.2 连续推进

选择连续推进后，“推进下一个任务”按钮从 DOM 中移除。系统可以取消人工点击等待，但不能跳过范围校验、远程 UT、CR 或提交；所有证据通过后才自动进入下一子任务。

## 11. 子任务 Git 提交协议

每个实施子任务使用 Conventional Commits 标题，摘要必须为中文。格式为：

```text
<type>: <中文摘要>

<work-id>-task<序号>
```

示例：

```text
feat: 增加内部重试风险场景判断

optimize-order-risk-check-task1
```

允许的常见类型包括 `feat`、`fix`、`refactor`、`test`、`docs` 和 `chore`。系统根据主变更类型建议提交类型，并在提交前展示完整信息。

提交硬门禁：

- 标题摘要为中文；
- 标题与任务标识之间保留空行；
- 任务标识与当前开发任务及子任务序号一致；
- 暂存区不包含当前子任务范围外文件；
- 当前远程 UT 和 CR 证据有效；
- `git commit` 成功并记录 SHA 后才可推进。

## 12. 最终测试、评审与 Push

所有实施子任务完成后执行完整的 BITS 远程 UT，并保存任务、代码 SHA、远程任务标识、结果和日志链接。不得用本地业务 UT 替代远程 UT。

完整远程 UT 通过后执行最终代码评审。最终 CR 必须校验：规格覆盖、计划完成度、修改范围、注释与实现一致性、日志可观测性、稳定性、安全性和测试证据。

只有完整远程 UT 与最终 CR 都关联当前 HEAD 且通过，才允许普通 `git push`。任一代码修改都会使对应证据失效并退回测试或评审。该流程不自动调用 `$cosh-before-push`，除非用户明确点名该 skill。

## 13. 实时观察板

### 13.1 导航与页面结构

顶部包含开发任务选择器和以下标签：

- 总览；
- 技术文档；
- 评审；
- 规格；
- 计划；
- 验证；
- Tasks。

Tasks 放在最右侧并使用高识别度强调色。原有独立 Artifacts 列表移除，产物直接通过对应标签查看。

任务页顶部放置推进模式切换。逐一任务校验模式下，当前任务卡片右上角显示唯一的“推进下一个任务”按钮；连续推进模式下该按钮从 DOM 中移除。任务列表直接解析 Superpowers 计划和进度，不重复展示一个 `tasks.md` 产物。

### 13.2 评审信息

评审页至少展示：

- 当前技术文档版本与评审轮次；
- AI-Spec 或通用规则降级状态；
- 稳定性、安全性、可行性三路进度；
- 未通过风险点、证据、影响和修改建议；
- 技术文档修改入口；
- 历史文档版本和历史评审结论；
- 当前阶段为何不能推进。

### 13.3 实时更新

监听器监控 Superpowers 原生产物、字节旁路状态、评审证据和 Git 状态。服务端通过 SSE 推送版本化状态；前端断线后自动重连，并在版本不连续时执行全量刷新。

服务端必须处理文件原子替换、短暂半写入、连续事件、删除和重建。解析失败时保留最后一个有效快照，同时将阶段标记为 `blocked` 并显示错误，不能将未知状态当成通过。

## 14. 本地复盘归档

### 14.1 触发方式

- 成功 push 后自动归档；
- 观察板提供“手动归档”，用于取消、终止或长期阻塞的开发任务。

### 14.2 单一复盘产物

归档生成一个 Markdown 文件，汇总：

- 开发任务、技术文档版本、规格、计划和提交；
- 总会话轮数以及各阶段轮数；
- 关键决策、用户修正和方案变化；
- 知识门禁、三路评审、文档修改与复审历史；
- 每个实施子任务的范围、远程 UT、CR 和 commit SHA；
- 完整测试、最终 CR、push 或终止结果；
- 阻塞、返工和范围变化节点。

会话数据来源与覆盖范围必须写入归档。运行环境能提供完整任务会话时记录精确轮数；只能观察 skill 启动后的交互时，明确标注起点和缺失范围，不估算未知轮数。敏感数据、凭证和完整隐私请求在归档前脱敏。

### 14.3 轮次原因分析

复盘按证据分析“为什么需要这么多轮”，至少覆盖：

- 需求或技术方案歧义；
- 代码事实不足；
- 知识门禁缺失或降级；
- 稳定性、安全性或可行性风险；
- 用户偏好或范围变化；
- 规格与代码不一致；
- 远程 UT 失败；
- CR 返工；
- 无关修改或范围扩大。

每个结论应引用对应阶段、轮次或证据，不能只输出泛化评价。

### 14.4 规则蒸馏

每条候选规则包含规则内容、本次证据、可减少的问题、适用范围、置信度和建议更新位置。规则只作为候选项展示，必须经人工“采纳规则”确认后才能进入后续 skill、reference 或模板修改任务；归档流程不得自动修改公共规则。

## 15. 后端控制接口

控制接口至少支持：

- 切换开发任务；
- 切换推进模式；
- 请求推进下一实施子任务；
- 提交技术文档新版本并触发重新评审；
- 生成手动归档。

每个写请求包含 `work-id`、期望状态版本和幂等键。服务端执行前置状态、文档哈希、代码 SHA、任务范围和证据校验。状态版本不一致时返回冲突，前端刷新后再操作。

## 16. 错误处理与恢复

- AI-Spec 安装或更新失败：记录原因并按规则进入显式降级门禁；
- CodeGraph 不可用：评审保持阻塞，不凭推测生成代码定位；
- 评审执行者失败：仅重试失败执行者，但技术文档版本变化后必须重跑全部三路；
- 远程 UT 服务失败：区分基础设施失败与测试失败，两者都不视为通过；
- CR 证据缺失或过期：阻止提交与推进；
- Git 暂存区污染：展示范围外文件并阻止自动提交；
- SSE 断连：前端重连并校验状态版本；
- 归档失败：不撤销已经成功的 push，但在任务上标记待补归档并允许重试。

## 17. 测试策略

实现采用测试先行，先把旧字节 OpenSpec 契约改为新的 Superpowers 契约并观察失败，再迁移实现。

至少覆盖：

1. skill 目录、frontmatter、agent 配置与资源链接校验；
2. 字节新 skill 中不存在旧 OpenSpec 产物或流程引用；
3. 原生规格、计划和 SDD 进度解析；
4. 多开发任务发现、切换和 `work=` URL；
5. 每个阶段的合法与非法状态转换；
6. 技术文档修改使知识门禁和三路评审全部失效；
7. 三路评审缺一路、失败或证据过期时不能生成规格；
8. 逐一任务校验的范围锁、远程 UT、CR、提交和解锁顺序；
9. 连续推进隐藏按钮但不跳过门禁；
10. Conventional Commits 中文标题、空行和任务标识校验；
11. 无关暂存文件阻止提交；
12. 最终远程 UT 与最终 CR 未通过时拒绝 push；
13. SSE 初始快照、增量更新、断线重连、文件替换与半写入恢复；
14. 自动与手动归档、gitignore、轮数覆盖声明、脱敏和规则候选；
15. 通用 `cosh-requirement-review-planner` 回归测试，确保通用 OpenSpec 能力不被迁移破坏。

## 18. 迁移边界

本次只迁移字节专属 skill：

- `cosh-byted-openspec-review-planner` 重命名并改造为 `cosh-byted-superpowers-review-planner`；
- 字节观察板脚本、参考资料和测试同步重命名；
- 删除字节目录内旧 OpenSpec 专属协议和术语；
- 保留并回归验证通用 `cosh-requirement-review-planner`；
- 不修改 Superpowers 插件自身文件；
- 不在本次迁移中自动采纳归档蒸馏出的规则。

## 19. 验收标准
