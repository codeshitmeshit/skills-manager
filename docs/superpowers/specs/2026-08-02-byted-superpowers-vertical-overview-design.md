# 字节 Superpowers 观察板竖向总览设计

## 背景

当前总览将十三个研发阶段放在四列卡片网格中。卡片能表达单个阶段状态，但无法直观表达严格的先后顺序、上游阻塞与下游等待之间的关系。用户需要把阶段竖向串联，优先看清“当前走到哪里、为什么停住、下一步是什么”。

## 目标

- 将总览阶段区改为单条竖向 Stepper，按后端返回顺序展示全部阶段。
- 用连线、图标、颜色和文本共同表达状态，不只依赖颜色。
- 在同一视区提供所选阶段的证据、阻塞原因、修复建议、版本和更新时间。
- 保留现有导航、当前阶段 Hero、任务进度和后端 API，不改变流程状态或门禁语义。
- 在桌面与移动端都保持清晰可用。

## 非目标

- 不修改评审、Tasks、验证等其他页签的布局。
- 不新增或修改后端状态字段、控制接口和 SSE 协议。
- 不允许总览页面直接推进任务或绕过门禁。
- 不改变 `passed`、`running`、`blocked`、`pending` 的业务定义。

## 页面结构

Hero 下方使用两列布局：左侧为竖向阶段 Stepper，右侧为阶段详情面板。

左侧每个阶段节点包含状态图标、中文阶段名、状态文本和简短摘要。节点之间使用连续竖线连接，顺序严格沿用 `data.stages`。状态语义如下：

- `passed`：绿色对勾，表示证据有效且门禁已通过。
- `running`：黄色实心节点，表示当前正在执行。
- `blocked`：红色叉号，表示当前阶段存在真实阻塞。
- `pending`：灰色空心节点，表示尚未到达或等待上游，不渲染成失败。

默认选中第一个 `running` 或 `blocked` 阶段；如果没有，则选择第一个未通过阶段；全部通过时选择最后一个阶段。用户点击任一阶段时，只更新右侧详情，不产生网络写请求。

右侧详情面板展示：

- 阶段中文名与状态；
- 第一条阻塞原因；
- `fix` 修复建议；
- `version` 和 `updated_at`；
- `can_advance` 是否允许继续。

没有对应信息时展示明确空状态，不使用占位符或虚构证据。详情面板在桌面端保持可见；移动端排列到 Stepper 下方。

## 交互与无障碍

- 阶段节点使用原生 `button`，支持键盘聚焦与激活。
- 当前选择使用 `aria-current="step"`，状态图标提供隐藏文本或可读标签。
- 选中态和焦点态不只依赖颜色，应有边框或背景差异。
- SSE 推送新快照后重新选择当前关键阶段；如果用户选中的阶段仍存在且状态未被流程推进淘汰，可以保留选择。
- 总览阶段选择仅存在于前端内存，不写入 URL 或后端状态。

## 响应式布局

- 宽屏：Stepper 与详情面板使用约 `minmax(280px, 0.8fr) / minmax(0, 1.2fr)` 两列。
- 窄屏：切换为单列，Stepper 在上、详情在下。
- 不压缩阶段名称；长阻塞信息允许换行。
- 删除总览页旧的四列 `.stage-grid` 布局，但保留 `.stage-card` 给验证页复用。

## 实现边界

- `assets/dashboard/app.js`：新增 Stepper 与阶段详情渲染函数，调整 `renderOverview`，绑定只读阶段选择事件。
- `assets/dashboard/styles.css`：新增 Stepper、节点、连接线、详情面板和响应式样式。
- `tests/test_byted_superpowers_dashboard.py`：验证竖向结构、四种状态语义、默认选择、详情内容和不产生控制写请求。

不修改 Python 服务端和工作流状态投影。

## 错误与边界情况

- `data.stages` 为空时展示“尚无阶段数据”，不抛出前端异常。
- 未识别状态按 `pending` 的视觉语义处理，同时展示原始转义后的状态文本，避免误判为通过。
- 阻塞原因和修复建议必须经过现有 `escapeHtml`。
- SSE 重绘不得重复注册事件或丢失页面其他控制行为。

## 验证

- 运行字节观察板定向测试，覆盖静态结构与渲染契约。
- 运行完整 `tests/test_byted_superpowers_dashboard.py`。
- 在本地演示任务上检查宽屏和窄屏总览，确认阶段顺序、连接线、选中态和详情联动。
- 确认评审、规格、计划、验证、Tasks 页签仍能正常渲染与操作。
