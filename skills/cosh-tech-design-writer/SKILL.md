# 字节技术方案编写

## 目标

把用户提供的零散技术内容或半成品方案整理成两类飞书文档：

- 技术方案文档：严格对照字节技术方案模板编写，正文保持正式、干净、可评审，不写问题、TODO 或 CR 意见。
- 问题文档：记录缺失章节、缺失原因、待确认项、风险、三路 subagent 交叉评审意见和最终审批结论。

## 自主处理与交互边界

- 默认先读资料和代码，再自行补齐、修正技术方案。P1/P2 风险只要有证据、在已授权范围内且不改变业务目标或权限边界，由主 Agent 修正方案、伪代码和调用图，再交原评审视角复审；P3 同样直接处理，不逐项请用户选择。
- 只有需要业务取舍、范围变更、安全/合规授权、预算或 SLA 承诺、不可逆迁移、接受剩余风险，或穷尽可用资料后仍缺少关键业务事实时，才向用户提问。多个技术实现路径本身不是提问理由；优先复用现有能力并选择最小修改面。
- 自主处理不是接受风险、修改业务代码或执行上线。P0 立即报告并阻止定稿；其他等级的未解决阻塞项也不得放行。修正后必须以证据复审，禁止自行降低等级掩盖问题。
- 问题文档记录每项风险的原始等级、处理方式（自主修正/用户决策/待补证据）、依据、回填位置、复审结论和剩余风险。已解决项汇总展示，不占用逐题交互。
- 同一问题连续两轮修正仍无有效进展时停止自动循环，说明尝试、剩余阻塞与需要的决策或资料，不重复询问已确认事项。
- 以下流程和 references 中的“确认/追问”均先按本节筛选；不得为填满模板或等待 subagent 而机械提问。

## 前置规则

- 默认模板使用 [references/default-template.md](references/default-template.md)。如果用户提供新的模板链接，先读取用户模板并覆盖默认模板结构。
- 本 skill 只用于编写和评审技术方案，不执行代码实现；在目标代码仓库中只能读取、搜索和分析文件，不得修改业务代码、配置、测试、脚本或生成补丁。
- 最终技术方案必须严格按本次使用的示例模板生成：章节标题、层级和顺序不得擅自删除、改名、合并或重排；不涉及的章节也必须保留，并写明“本方案不涉及，原因是……”。
- 具体方案必须写具体实现，不能泛泛而谈；无法确定实现细节时，先调查证据并自主设计；确需用户决策时才按确认问题流程提问，不得用空泛描述占位。
- 技术方案涉及代码改动时，必须读取 [references/code-change-implementation-rules.md](references/code-change-implementation-rules.md)，并在详细方案中写出具体逻辑实现。
- 当前任务发生在代码仓库中，或涉及新接口、接口改造、函数命名、代码风格、语言规范时，必须读取 [references/codebase-inspection-rules.md](references/codebase-inspection-rules.md)，先基于真实代码确定改动点和命名风格。
- 在代码仓库内生成方案时，最终技术方案的每一个具体实现点都必须给出面向当前仓库的落地实现：明确在哪个文件、哪个函数/方法/配置项下实现，插入或修改哪个逻辑分支，并提供贴近仓库语言风格的伪代码；代码勘察证据用于支撑这些实现结论。
- 审批结论必须遵守默认模板中的“阻塞判定规则”；命中任一阻塞项时不得给出“通过”或“有条件通过”。
- 对需要用户确认的缺口和风险，必须读取 [references/confirmation-question-rules.md](references/confirmation-question-rules.md)，并把问题文档中的待确认项改写成可回答的问题。
- 向用户追问时一次只问一个确认问题；只有当前运行环境明确提供原生选择题/用户输入工具时，才使用点击式选项，否则用 A/B/C/D 文本选项退化，不要假设 Codex Desktop 普通消息会渲染成按钮。
- 用户提供 PRD、需求文档、会议纪要、长篇背景资料或多个参考链接时，优先启动背景资料阅读 subagent 做结构化摘要；主流程继续推进不依赖资料全文的草稿整理，等摘要返回后再补齐背景、目标、范围和待确认项。
- 代码仓库勘察 subagent 运行期间，主流程不要长时间空等；优先推进不依赖勘察结果的草稿、图表和资料整理，等 subagent 返回后再合并事实、修正草稿和问题文档。
- 技术内容存在调用链、业务流程、模块交互、状态流转或异步链路时，必须读取 [references/mermaid-diagram-rules.md](references/mermaid-diagram-rules.md)，并在技术方案对应章节生成 Mermaid 图。
- 用户要求图以图片形式进入飞书文档，或最终飞书技术方案包含 Mermaid/PlantUML/SVG 图且需要图片化展示时，必须读取 [references/diagram-image-append-rules.md](references/diagram-image-append-rules.md)，将图渲染为图片后追加到对应飞书文档；不要只留下代码块。
- 用户要求 Mermaid 转成飞书画板内容、输出可插入飞书文档的画板 XML、或写入已有飞书画板时，必须读取 [references/mermaid-whiteboard-output-rules.md](references/mermaid-whiteboard-output-rules.md)，区分“输出文档画板块”和“更新已有画板”两种路径。
- 启动 subagent 前必须读取并使用 [references/subagent-review-prompts.md](references/subagent-review-prompts.md) 中的 prompt 规范，不要只给一句笼统任务。
- 写飞书文档前必须使用 `lark-doc` skill；如需解析 Wiki 节点，使用 `lark-wiki`，但正文读取和创建仍以 `lark-doc` 为准。
- 项目背景是正式技术方案的必填前置条件；如果背景缺失或只有一句无法支撑方案的描述，先从现有资料补齐，确实缺少业务事实时再追问，不能直接创建正式技术方案。
- 优先使用用户提供的文档标题；未提供时根据明确的需求主题拟定标题，不单独追问标题。最终技术方案文档标题必须规范化为 `【技术方案】{标题}`；若用户已提供 `【技术方案】` 前缀，不要重复添加。
- 创建正式技术方案文档前，必须先在对话中给出模板对照结果、方案草稿摘要和问题文档摘要，；只有存在待用户决策项或缺少外部写入授权时才等待确认。
- 技术方案正文不得混入评审问题。所有问题、风险、缺口和审批结论都写入同一篇问题文档。
- 完成技术方案草稿后，必须启动 3 个 subagent 做交叉评审；如果当前环境没有可用 subagent 工具，明确说明降级为主 Agent 的三轮独立评审。
- 最终创建技术方案文档前，如果方案发生在代码仓库中或涉及代码改动，必须启动 1 个程序员落地性复核 subagent，只读仓库并核对每个实现点的目标文件、函数、插入位置、伪代码和流程图是否真实可落地。
- Subagent 交叉评审未基本通过时，不得创建最终技术方案文档；必须先自主修正可处理项、回填方案并重新 review；只对需要用户决策的问题提问。

## 工作流

1. 收集输入
   - 读取用户提供的技术内容、半成品方案、模板链接、目标文档标题和期望输出位置。
   - 如果缺少标题，根据需求主题拟定标题。
   - 将用户提供的标题规范化为 `【技术方案】{标题}`，并将该规范化标题用于技术方案文档创建和后续摘要。
   - 问题文档标题规范化为 `【问题清单】{标题}`，其中 `{标题}` 使用本次确定的标题主体；如果用户标题已包含 `【技术方案】` 前缀，先去掉该前缀再拼接，避免生成 `【问题清单】【技术方案】{标题}`。
   - 如果用户给出模板链接，读取该模板；否则读取默认模板 reference。
   - 如果用户提供 PRD、需求文档、会议纪要或长篇背景资料，启动背景资料阅读 subagent，总结业务背景、目标、范围、约束、验收标准、风险和可映射模板章节；subagent 运行时，继续整理可确定的模板章节；仅对必要的输出授权或业务决策提问。
   - 如果当前目录是代码仓库，或用户提到新接口/代码改动，先执行代码仓库勘察；必要时启动若干个 subagent 分片阅读相关代码。subagent 运行时，继续整理不依赖代码事实的草稿；不为等待勘察而追加问题，不要等待所有勘察完成后才问下一个问题。
   - 代码仓库勘察必须是只读操作；不得在目标仓库中运行会修改文件的格式化、生成、测试修复、补丁应用或代码编辑命令。
   - 代码勘察完成前，不得生成带具体文件名、函数名、配置 key、错误码或测试位置的最终详细方案；只能写为待确认项或草稿假设。代码勘察完成后，必须把每个代码事实写进对应实现点的具体实现说明，而不是只罗列证据。

2. 模板对照
   - 将用户输入逐项归类到模板章节。
   - 输出“已覆盖 / 缺失 / 需确认”的对照表。
   - 对缺失章节写明缺失原因，例如“用户未提供容量指标”“涉及安全高风险，不能推断”。

3. 补充追问
   - 项目背景缺失时，先查已有资料，仍缺关键事实才追问背景；至少明确业务上下文、现状问题、触发原因、目标用户或影响范围。
   - 核心章节不足时，先自行调查补齐；未解决的阻塞项不得进入正式文档。
   - 核心章节包括：背景故事、业务目标、技术目标、方案总览、详细设计、接口与存储、关键技术决策 Q&A、稳定性与安全 Q&A、测试用例、灰度上线方案和容量评估。
   - 低风险内容可基于上下文谨慎推断；高风险内容先调查证据并写入问题文档，仅需用户决策时追问，不得强行填充。高风险内容包括安全、权限、敏感数据、容量、性能、兼容性、上线风险、数据迁移、回滚和对上游业务影响。
   - 仅对必要决策提问；能枚举时给出 2–3 个真实选项和推荐原因，不凑数。无法枚举时简短询问所缺事实。一次只问一个必要问题，遵守当前输入工具的使用限制。
   - 背景资料阅读 subagent 未返回时，只追问不依赖资料全文的问题；依赖 PRD 目标、用户范围、验收标准、业务约束或需求优先级的问题，等摘要返回后再问。
   - 代码勘察 subagent 未返回时，只追问不依赖代码事实的问题；依赖文件名、函数名、接口风格、错误码、数据模型或测试位置的问题，等勘察结果返回后再问。

4. 生成技术方案草稿
   - 严格按照本次示例模板生成，不得删减、改名、合并、重排模板章节；用户提供模板时以用户模板为准，未提供时以默认模板为准。
   - 明显不适用的章节仍保留，并写“本方案不涉及，原因是……”；原因必须具体到本需求边界、系统范围或变更类型，不能只写“不涉及”。
   - 具体方案必须说明“谁在什么时机，通过什么入口，读取/写入什么数据，调用哪些模块，如何处理成功/失败，如何观测和回滚”；禁止只写“优化流程”“新增能力”“调整逻辑”等泛化描述。
   - 无法确认具体实现时，不要猜测；先勘察并自主设计，记录缺口，仅将必须由用户决定的阻塞项转成问题。
   - 如果方案涉及代码改动，在“四、详细设计”的每个具体实现点中写清当前仓库的落地实现，包括改动模块、目标文件、目标函数/方法/配置项、插入位置、核心分支、数据读写、错误处理、幂等、兼容和伪代码；伪代码必须使用 fenced code block 包裹，并标注合适语言或 `text`。
   - 如果方案发生在本地代码仓库中，“四、详细设计”的每个具体实现点都必须说明“在哪改、改什么、怎么改”，并在同一实现点内给出代码勘察证据；不要用单独的证据清单或总表替代逐点实现说明。
   - 如果涉及新接口或接口改造，接口命名、路径、方法名、请求/响应结构、错误码、handler/service/repository 分层必须和原代码仓库保持一致，并说明依据来自哪些现有代码模式。
   - 如果输入中存在调用逻辑或模块交互，在对应章节插入 Mermaid 图，通常放在“三、方案总览：一张图看懂整体设计”“四、详细设计”“六、稳定性与安全 Q&A”或“七、测试用例与上线方案”。
   - 明确写出变更影响面：上游、下游、接口、数据表、配置、权限、缓存、异步任务、监控告警、SLA、上线和回滚影响；不涉及项写明原因。
   - 缺失但不阻塞成稿的章节，在正式方案中只写可确认的中性描述；缺口详情放入问题文档。
   - 保持技术方案正文正式、可直接用于评审，不出现“待补充”“TODO”“问题如下”等问题清单口吻。

5. 草稿摘要与必要决策
   - 在创建飞书文档前，向用户展示：
     - 技术方案草稿摘要。
     - 模板覆盖情况。
     - 将写入问题文档的缺口和风险摘要。
   - 无待用户决策项时直接进入交叉评审；有决策项时等回答并回填。用户已要求生成飞书文档且目标明确时不重复索要创建许可；仅要求本地草稿或评审不等于授权外部写入。

6. 三路 subagent 交叉评审
   - 技术方案草稿完成后、最终文档创建前，启动 3 个 subagent 评审同一份方案。
   - 每个 subagent 的 prompt 必须包含：评审角色、输入材料、评审边界、严重程度规则、输出表格格式、禁止事项和审批建议。
   - 三个评审视角必须不同：
     - 安全性与合规：鉴权、权限边界、敏感数据、加密、审计、数据泄露风险。
     - 技术合理性与架构完整性：方案选型、接口边界、存储设计、异常处理、兼容性、可维护性。
     - 性能与稳定性：容量、调用链、缓存、限流降级、监控告警、上线和回滚风险。
   - 每个 subagent 输出问题项、所属章节、严重程度、原因、建议补充内容、是否阻塞评审。
   - 汇总去重后写入同一篇问题文档。

7. 评审后回填
   - 读取 3 个 subagent 的评审结果，区分“可确定改进”和“问题/风险/TODO”。
   - 对无争议、事实明确、不会引入臆测的改进，回填到技术方案正文对应章节。
   - 对仍未解决的风险或信息缺口保留问题记录；已通过证据确认的修正回填正文，只有需要用户决策的事项才追问。
   - 存在 P1/P2 或 subagent 建议 `暂不通过` 时，先按自主处理边界修正并复审，不因等级或结论自动提问；P0 立即报告并阻塞定稿。
   - 自主修正或用户回答后，更新问题文档状态，将可确定内容回填技术方案，并重新启动对应视角或全部 subagent review。
   - 有有效进展时继续修正复审，直到无阻塞且至少“有条件通过”；无进展时按自主处理边界停止。如果用户明确接受剩余非阻塞风险，记录为 `接受风险`。
   - 回填后再次检查 Mermaid 图、变更影响面、核心章节和问题文档是否一致。

8. 程序员落地性复核
   - 如果方案发生在代码仓库中，或包含代码改动、新接口、配置变更、逻辑分支调整、测试变更，最终创建文档前必须启动 1 个程序员落地性复核 subagent。
   - 该 subagent 必须只读仓库，到具体文件/函数/配置位置核对每个实现点，确认目标文件、目标函数/方法/配置项、插入位置、核心分支、错误处理、测试点、伪代码和 Mermaid 流程图是否真实可落地。
   - subagent 输出必须包含：实现点、目标文件、目标函数/方法/配置项、核对结论、需要修正的内容、建议伪代码、建议 Mermaid 图、是否阻塞生成最终文档。
   - 对 subagent 明确指出的可确定修正、建议伪代码和建议 Mermaid 图，必须回填到技术方案正文的对应实现点；不能只保留在复核结果或问题文档中。
   - 存在多种实现路径时，基于代码证据与最小修改面自行选择并复核；仅涉及用户决策的路径差异才追问，结论必须回填对应实现点。
   - 如果程序员落地性复核存在阻塞项，不得创建最终技术方案文档；必须修正方案并重新复核，直到无阻塞项或用户明确接受非阻塞风险。

9. 创建文档和输出审批结论
   - 基于主流程缺口和 3 个 subagent 评审结果，给出审批结论：
     - 通过：无阻塞问题，仅有少量非阻塞优化建议。
     - 有条件通过：存在非阻塞待补充项，补齐后可评审通过。
     - 暂不通过：存在阻塞问题，例如安全、容量、兼容、上线回滚或核心设计缺失。
   - 命中任一阻塞判定规则时，必须给出“暂不通过”。
   - 只有审批结论达到“通过”或“有条件通过”时，才创建最终技术方案文档和问题文档。
   - 如果需要程序员落地性复核，只有复核结论无阻塞项时，才创建最终技术方案文档和问题文档。
   - 如果用户要求图以图片形式追加，或飞书文档需要图片化呈现图表，创建技术方案文档后按图表图片追加规则渲染并插入图片；渲染失败时不要谎称已插入，必须把原因写入问题文档或最终回复。
   - 如果用户要求输出或写入飞书画板内容，创建或更新文档时按 Mermaid 画板输出规则生成 `<whiteboard type="mermaid">` XML 块，或使用 `lark-cli whiteboard +update --input_format mermaid` 写入已有画板，并在最终回复中给出输出内容或画板 token/更新结果。
   - 如果多轮追问后仍为“暂不通过”，不要创建最终技术方案文档；只输出当前草稿、问题清单和继续补充的问题。
   - 审批结论必须写入问题文档末尾，并在最终回复中简要说明。

## 问题文档要求

问题文档标题使用 `【问题清单】{标题}`，例如 `【问题清单】订单状态同步改造`。`{标题}` 使用本次确定的标题主体；如果用户标题已包含 `【技术方案】` 前缀，先去掉该前缀。

问题文档必须包含：

- 模板覆盖总览。
- 缺失章节及缺失原因。
- 需用户确认的问题。
- 主 Agent 初审风险。
- 三个 subagent 的分视角评审结果。
- 汇总后的阻塞问题和非阻塞问题。
- 最终审批结论。

问题项格式：

```markdown
| ID | 来源 | 章节 | 原始严重程度 | 问题 | 证据 | 处理方式 | 修正与回填位置 | 是否阻塞 | 复审结论 | 剩余风险 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
```

严重程度使用：`P0 阻塞`、`P1 高`、`P2 中`、`P3 低`。
状态使用：`待补证据`、`待用户决策`、`已修正待复审`、`接受风险`、`不适用`、`已关闭`。修正不能直接标为关闭，必须保留复审通过的依据。

## 输出规则

- 最终至少返回技术方案文档链接和问题文档链接；若仍未基本通过，则返回草稿和问题清单，不创建最终文档。
- 如果因为权限、认证或用户未确认导致无法创建飞书文档，输出当前草稿、问题清单和明确的下一步。
- 如果使用了用户提供的新模板，最终说明已使用该模板覆盖默认模板。
- 不要创建 README、安装说明、变更日志或无用占位文件。

## 质量检查

交付前确认：

- 技术方案标题来自用户输入或明确的需求主题。
- 最终技术方案文档标题格式为 `【技术方案】{标题}`，且没有重复前缀。
- 问题文档标题格式为 `【问题清单】{标题}`，且没有叠加 `【技术方案】` 前缀。
- 项目背景已补齐，且至少说明业务上下文、现状问题、触发原因、目标用户或影响范围中的 3 项。
- 技术方案保留模板全部章节。
- 技术方案章节标题、层级和顺序与本次示例模板一致，没有擅自删减、改名、合并或重排。
- 不适用章节仍保留，并有具体的“不涉及”原因。
- 具体方案写出了可评审的实现细节；没有用泛化描述替代具体实现。
- 不确定实现已先调查并自主处理；确需用户决策的事项才进入追问。
- 在代码仓库内设计方案时，已基于真实代码识别改动点、命名风格、接口风格和语言规范；涉及新接口时，方案说明了与现有代码风格一致的依据。
- 代码仓库内生成的方案在每个具体实现点内都明确目标文件、目标函数/方法/配置项、插入位置、具体逻辑和伪代码。
- 每段伪代码都使用 fenced code block 包裹，不能写成普通段落、行内代码或列表项。
- 代码仓库内生成的方案在每个具体实现点内都标注了代码勘察证据；每个文件名、函数名、接口、配置 key、错误码和测试位置都有本地代码读取或 subagent 事实输出支撑，但证据不能替代逐点实现说明。
- 涉及代码改动时，详细方案包含具体逻辑实现，而不是只有架构描述或背景说明。
- 存在调用逻辑时，技术方案对应章节包含可渲染的 Mermaid 图；若无法画图，问题文档记录缺失原因和需要补充的信息。
- 如果用户要求图以图片形式进入飞书文档，Mermaid/PlantUML/SVG 已渲染为图片并通过 `lark-cli docs +media-insert` 追加到技术方案文档；失败时已说明具体失败原因和保留的降级产物。
- 如果用户要求 Mermaid 转飞书画板内容，已输出可插入文档的 `<whiteboard type="mermaid">` XML 块，或已用 `lark-cli whiteboard +update --input_format mermaid` 写入已有画板并记录结果；失败时已说明缺失的 doc/token/权限或语法问题。
- 技术方案包含变更影响面分析，覆盖上游、下游、接口、数据、配置、权限、缓存、任务、监控、SLA、上线和回滚影响。
- 技术方案正文没有问题清单、CR 意见、TODO 或审批结论。
- 问题文档包含缺失章节、缺失原因、风险、待确认项、处理状态、三路 subagent 评审和审批结论。
- 问题文档中的待确认项已转成选择题，且包含合理选项、建议选项、建议原因、确认原因和不确认风险；无法枚举时说明为何使用短答。
- 已按单题交互节奏追问用户；支持点击式选项时已使用原生选择控件。
- 长篇 PRD、需求文档、会议纪要或背景资料已通过 subagent 摘要后再回填，且等待期间已继续推进非强依赖的文档整理。
- 代码勘察 subagent 运行期间已继续推进非强依赖的文档整理，没有因等待勘察结果而阻塞整个澄清流程。
- Subagent 评审后的可确定改进已回填技术方案正文；待确认项仍保留在问题文档。
- 若 subagent 评审未基本通过，已修正可自主处理的风险并重新 review，仅对必要决策提问。
- 涉及代码仓库或代码改动时，最终文档创建前已完成程序员落地性复核；每个实现点的文件、函数、插入位置、伪代码和 Mermaid 图建议已被核对。
- 程序员落地性复核给出的可确定修正、建议伪代码和 Mermaid 图已落实到技术方案正文对应实现点，而不是只记录在复核结果或问题文档。
- 最终文档只在审批结论达到“通过”或“有条件通过”后创建。
- 审批结论符合阻塞判定规则。
- 三个 subagent 的评审角度不同，且结论已去重汇总。
- 三个 subagent 使用了规范化 prompt，输出字段一致，且没有直接修改技术方案正文。
- 高风险内容没有被无依据推断。
- 创建飞书文档前已具备明确的写入授权和目标；没有重复索要已有授权。
- 未修改目标代码仓库文件；如发现需要真实代码改动，只在技术方案中说明实现方式和伪代码。
