# 代码改动实现细节规则

当技术方案涉及代码改动、接口改造、逻辑分支调整、任务/脚本新增、存储读写变化、缓存变更、权限判断变更或配置开关变更时，详细方案必须写出具体逻辑实现。

如果当前任务发生在代码仓库中，必须先按 [codebase-inspection-rules.md](codebase-inspection-rules.md) 勘察真实代码，再写具体逻辑实现。具体逻辑实现必须贴近仓库语言、框架、分层和命名风格。

本 skill 不负责真正实施代码改动。即使已定位目标文件和函数，也只能在技术方案中写出实现方式、伪代码、测试点和影响面，不得修改目标仓库文件或生成补丁。

## 必须写入技术方案正文

在 `四、详细设计` 中至少覆盖：

- 逐点落地实现：每个具体实现点必须明确目标文件、目标函数/方法/配置项、插入位置、具体逻辑、伪代码和测试点；伪代码必须使用 fenced code block 包裹，并标注合适语言或 `text`。
- 逐点代码证据：每个具体实现点必须说明文件、函数、接口、配置、错误码或测试位置来自哪里，支撑什么实现结论。
- 改动模块：涉及哪些服务、包、文件、类、函数、接口、任务或配置。
- 调用入口：请求、任务、事件、回调、消费消息或定时调度从哪里进入，以及落在哪个入口函数/方法。
- 命名与风格依据：参考哪些现有函数、类型、接口、错误码、目录或测试。
- 核心逻辑：按执行顺序描述主要分支、判断条件、状态变化和返回结果。
- 数据读写：读取和写入哪些数据、字段、缓存、索引或中间状态。
- 幂等与一致性：重复请求、重试、并发、事务、补偿、最终一致性如何处理。
- 异常处理：下游失败、超时、参数非法、数据不存在、部分成功时如何处理。
- 兼容逻辑：老数据、老接口、旧配置、灰度期间双写/双读/降级如何兼容。
- 开关与灰度：是否需要配置开关、实验开关、租户/用户/流量维度灰度。
- 可观测性：关键日志、监控指标、trace、报警和排查入口。
- 测试点：核心单测、集成测试、回归 case 和异常 case。

## 推荐表达形式

优先使用以下结构：

````markdown
### 4.x 代码改动逻辑实现

#### 实现点 1：<实现点名称>

- 目标文件：`<path>`
- 目标函数/方法/配置项：`<symbol>`
- 插入位置：<在函数开始/参数校验后/现有分支前/错误处理处/配置解析处等>
- 具体实现逻辑：<按当前仓库代码结构说明具体改动>
- 数据读写：<读取/写入的数据、字段、缓存或配置>
- 异常与兼容：<错误处理、灰度、兼容、回滚>
- 测试点：<需要补充或修改的测试>
- 代码证据：<主 Agent 读取的文件/符号或 subagent 输出>

#### 命名与风格依据
| 设计项 | 拟定命名/结构 | 参考的现有代码模式 | 证据来源 |
| --- | --- | --- | --- |

#### 核心执行流程
1. <入口>
2. <校验和分支>
3. <核心读写>
4. <返回/异步处理>

##### 伪代码
```text
// <目标文件>:<目标函数/方法>
function existingFunction(input):
    // 保留现有校验/前置逻辑
    validate input

    // 新增分支：<说明触发条件>
    if matchNewCondition(input):
        // 读取/转换/校验新增数据
        data = loadOrBuildNewData(input)
        if invalid(data):
            return existingErrorStyle(...)
        return existingSuccessStyle(data)

    // 保留原有分支
    return legacyPath(input)
```
````

如果 Mermaid 更适合表达调用顺序，同时补充 Mermaid 图；但 Mermaid 不能替代每个实现点中的“目标文件 + 目标函数 + 插入位置 + fenced code block 伪代码”。

## 信息不足时

如果用户没有提供足够的代码实现信息，不要编造模块名、函数名或字段。必须在问题文档中生成选择题确认，例如：

```markdown
| ID | 章节 | 确认问题 | 选项 | 建议选项 | 建议原因 | 为什么需要确认 | 不确认风险 | 优先级 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Q-CODE-001 | 四、详细设计 | 新逻辑应该接入在哪个入口？ | A. 现有同步接口入口；B. 异步消息消费入口；C. 定时任务入口；D. 其他，请说明。 | A/B/C 由用户按真实调用链确认 | 入口决定调用链、幂等、异常处理和监控埋点。 | 无法写出具体逻辑实现，详细方案不可评审。 | P0 阻塞 | 待确认 |
```

## 阻塞规则

代码改动型方案如果缺少具体逻辑实现，审批结论必须是 `暂不通过`。只写“新增逻辑”“调整判断”“优化流程”“调用下游”等泛化描述，不算具体逻辑实现。
