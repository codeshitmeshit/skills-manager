# 代码仓库勘察与接口改动规则

当用户在代码仓库中进行技术方案设计，或方案涉及新接口、接口改造、函数命名、代码风格、语言规范、模块边界或具体改动点时，必须先基于真实代码勘察，再写技术方案。

本规则只允许只读勘察。不得修改目标仓库中的任何业务代码、配置、测试、脚本或文档；不得应用 patch、运行格式化写回、生成代码文件或执行自动修复。需要改动时，只在技术方案中描述目标文件、目标函数、插入位置、具体逻辑和伪代码。

## 勘察目标

在生成技术方案前，明确：

- 仓库语言、框架、目录结构和分层模式。
- 现有接口定义方式，例如 HTTP route、RPC/IDL、GraphQL、CLI command、消息消费、定时任务。
- 现有命名风格，例如 handler、service、manager、repository、model、DTO、错误码、常量、配置项。
- 现有代码组织方式，例如参数校验、鉴权、日志、监控、错误处理、事务、缓存、测试目录。
- 新需求最可能改动的模块、函数、文件、接口、配置、测试和文档。
- 对应语言的开发规范，例如 Go/Java/TypeScript/Python 的错误处理、命名、并发、空值、类型、测试习惯。

## Subagent 分片阅读

涉及真实代码仓库且范围不清时，必须启动若干个 subagent 分片阅读代码。建议按以下维度拆分：

- 接口入口 subagent：查找 route、controller、handler、IDL/proto/OpenAPI、参数校验和鉴权入口。
- 业务逻辑 subagent：查找 service、manager、domain、usecase 等核心逻辑层。
- 数据与依赖 subagent：查找 repository、DAO、model、缓存、消息、下游 client、配置和错误码。
- 测试与规范 subagent：查找现有测试写法、mock、fixture、lint/style、命名和语言习惯。

启动这些 subagent 时，必须使用 [subagent-review-prompts.md](subagent-review-prompts.md) 中的“代码仓库勘察 Subagent Prompt”，不要只给一句笼统的“去看代码”。

每个 subagent 只输出事实，不直接写方案。输出必须包含：

```markdown
| 维度 | 发现 | 文件/符号 | 对技术方案的影响 |
| --- | --- | --- | --- |
```

如果无法启动 subagent，主 Agent 必须自己按上述维度阅读代码，并在问题文档中说明降级原因。

主 Agent 和 subagent 都只能使用只读方式查看代码，例如 `rg`、`sed`、`cat`、只读 IDE/代码导航或不会写回文件的命令。不要执行会改变工作区的命令。

## 代码证据硬约束

在本地代码仓库中生成技术方案时，主 Agent 必须保留代码勘察证据。任何写入技术方案正文的具体文件名、函数名、类型名、接口路径、配置 key、错误码、表/字段、测试文件或模块分层，都必须来自以下至少一种来源：

- 主 Agent 使用 `rg`、文件读取或代码导航实际读取到的本地代码。
- 代码勘察 subagent 返回的事实表格，且表格中包含文件/符号。
- 用户明确提供的代码事实，并且该事实已在问题文档中标注为用户提供。

禁止把未验证的代码路径、函数名、配置 key 或错误码写成确定结论。没有证据时，必须写入问题文档并转成确认问题，或标注为“待代码勘察确认”，不得进入最终技术方案正文。

技术方案的 `四、详细设计` 必须把代码事实写进每个具体实现点。每个实现点必须回答：在哪个文件、哪个函数/方法/配置项下实现，插入或修改哪个分支，具体逻辑是什么，伪代码怎么写，以及这些代码事实来自哪里。伪代码必须使用 fenced code block 包裹，并标注合适语言或 `text`。

````markdown
#### 实现点 N：<实现点名称>

- 目标文件：`<path>`
- 目标函数/方法/配置项：`<symbol>`
- 插入位置：<具体位置>
- 具体实现逻辑：<具体逻辑>
- 伪代码：<贴近仓库语言风格的伪代码>
- 测试点：<测试文件或测试类型>
- 代码证据：<主 Agent 读取或 subagent 输出>

```text
// <path>:<symbol>
<伪代码>
```
````

如果代码勘察尚未完成，不得输出包含具体代码位置的最终详细方案；只能输出草稿摘要和仍待确认的问题。代码勘察完成后，不得只罗列文件和函数，也不得只输出总表；必须在每个实现点内写出对应实现位置、实现逻辑、伪代码和代码证据。

## 并行追问规则

代码勘察 subagent 启动后，主 Agent 不要长时间等待。等待期间继续推进不依赖代码事实的确认问题，并明确告诉用户“代码勘察正在进行，先确认下一个不依赖代码结果的问题”。

等待期间可以追问：

- 文档标题、项目背景、业务目标、影响范围。
- 安全 BP、审批人、免审/灰度/上线策略等业务侧口径。
- 容量预估、排期、验收标准、测试关注点。
- 用户已提供但存在多种表达方式的非代码决策。

等待期间不要追问或直接定稿：

- 具体文件名、函数名、类型名、错误码、接口路径、IDL/RPC 方法名。
- handler/service/repository 分层归属。
- 现有鉴权、监控、日志、测试框架的具体复用方式。
- 任何必须依赖代码勘察事实才能判断的实现细节。

subagent 返回后，先合并事实并更新问题文档，再判断是否需要继续追问代码相关问题或修正技术方案草稿。

## 新接口设计要求

涉及新接口或接口改造时，技术方案必须写清：

- 接口类型：HTTP/RPC/IDL/消息/任务/CLI/内部函数。
- 命名依据：参考了哪些现有接口、函数、类型、错误码或目录命名。
- 路由或方法：路径、method、RPC method、topic、command 或函数签名。
- 请求结构：字段名、类型、必填性、默认值、校验规则、兼容策略。
- 响应结构：成功响应、错误响应、分页/游标、状态码或业务错误码。
- 鉴权与权限：复用哪套鉴权、是否新增权限点、权限失败如何返回。
- 幂等与重试：请求幂等 key、重复提交、下游重试、超时处理。
- 兼容与灰度：老接口/老字段兼容、灰度开关、双写/双读、回滚策略。
- 测试：单测、接口测试、契约测试、回归 case 和异常 case。

## 风格一致性规则

- 不自行发明命名风格；优先复用仓库现有同类接口和同层模块命名。
- 不跨层调用破坏原有架构；遵守现有 controller/handler -> service -> repository/client 等分层。
- 不引入与仓库主语言风格冲突的伪代码；伪代码应贴近仓库语言和框架。
- 不编造文件名、函数名、类型名；无法确认时写入问题文档并生成选择题确认。
- 若用户要求的接口风格和仓库现有风格冲突，必须在问题文档中标记风险，并给出选择题让用户确认是否接受不一致。

## 阻塞规则

命中以下任一情况时，审批结论必须是 `暂不通过`：

- 方案涉及新接口，但没有阅读仓库现有接口风格。
- 方案无法说明接口命名、请求/响应结构、错误码或鉴权如何对齐现有代码。
- 方案涉及代码改动，但无法定位改动模块、入口函数、核心逻辑层或测试位置。
- 方案提出的函数/类型/路径命名明显不符合原代码仓库风格，且没有迁移或兼容理由。

## 确认问题示例

```markdown
| ID | 章节 | 确认问题 | 选项 | 建议选项 | 建议原因 | 为什么需要确认 | 不确认风险 | 优先级 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Q-API-001 | 4.5 接口与存储 | 新接口应采用哪种入口风格？ | A. 复用现有 HTTP route/controller 风格；B. 复用现有 RPC/IDL method 风格；C. 作为内部 service 方法不暴露外部接口；D. 其他，请说明。 | A/B 以仓库现有同类接口为准 | 接口入口决定命名、鉴权、错误码、测试和调用链。 | 可能导致接口风格和仓库不一致，评审无法通过。 | P0 阻塞 | 待确认 |
```
