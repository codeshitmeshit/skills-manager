# 默认字节技术方案模板

当用户未提供新的模板链接时，按本模板生成技术方案。若用户提供模板链接，以用户模板为准。

本默认模板以用户指定的飞书示例文档 `https://bytedance.larkoffice.com/docx/BAgXdAai5o7VHuxrxYKcxYDAnLe` 为主，采用“背景故事 + 方案总览 + 详细设计 + Q&A 评审”的叙事化技术方案格式。

## 模板使用硬约束

- 最终技术方案必须严格保留本模板的章节标题、层级和顺序。
- 不要擅自删除、改名、合并或重排章节。
- 明显不适用的章节也必须保留，并写明：`本方案不涉及，原因是……`。
- “不涉及”原因必须具体说明和本需求边界、系统范围或变更类型的关系，不能只写“不涉及”。
- 如果用户提供新的示例模板，则同样严格遵守用户模板的章节标题、层级和顺序。

## 技术方案文档章节

0. 一句话摘要
   - 使用 callout 或开篇短段说明：要解决的问题、核心方案、影响主链路程度、灰度和回滚方式。

1. 一、背景故事：为什么要做这件事？
   - 业务/系统上下文
   - 正常流程或当前机制
   - 致命场景/触发问题
   - 直接后果
   - 当前替代方案及不足

2. 二、目标：这次要做成什么样？
   - 业务目标
   - 技术目标
   - 不做范围/边界（如有）

3. 三、方案总览：一张图看懂整体设计
   - 整体方案图（Mermaid 或飞书画板）
   - 核心路径一
   - 核心路径二
   - 核心路径三（按实际路径数量增减，但章节仍保留总览）
   - 核心设计原则

4. 四、详细设计
   - 4.1 核心路径一详细设计
   - 4.2 核心路径二详细设计
   - 4.3 核心路径三详细设计
   - 4.4 模块拆分与配置设计
     - 模块职责划分
     - 配置项/TCC/开关设计
   - 4.5 接口与存储
     - 接口影响
     - 存储设计
   - 如方案存在更多关键路径，继续按 `4.x` 补充；不涉及的路径写明不涉及原因。

5. 五、关键技术决策 Q&A
   - Q1：为什么选择当前方案，而不是更直接/更复杂的替代方案？
   - Q2：为什么采用当前粒度、边界或触发方式？
   - Q3：为什么不引入额外依赖或分布式组件？
   - Q4：关键异常或边界场景为什么这么处理？
   - Q5：对外接口、查询、同步/异步行为为什么这样设计？
   - 每个问题必须包含：结论、原因、代价。

6. 六、稳定性与安全 Q&A
   - 第一关：会不会影响主链路？
   - 第二关：出了问题怎么止损？
   - 第三关：数据一致性如何保证？
   - 第四关：安全与审计
   - 每个问题必须以 Q&A 形式回答，并覆盖容量、性能、降级、回滚、幂等、一致性、权限、安全、监控。

7. 七、测试用例与上线方案
   - 7.1 核心业务流程测试
   - 7.2 异常场景测试
   - 7.3 灰度上线方案
   - 7.4 容量评估

## 核心章节判定

项目背景是正式技术方案的必填前置条件。缺少背景时，不要创建正式技术方案；先追问并补齐。背景至少应覆盖以下信息中的 3 项：

- 业务上下文：方案发生在哪个业务、系统或流程中。
- 现状问题：当前痛点、缺陷、成本、风险或机会是什么。
- 触发原因：为什么现在要做，例如需求变化、规模增长、合规要求、历史债务、线上问题。
- 目标用户或影响范围：影响哪些用户、业务方、系统、上下游或数据。
- 当前替代方案：目前如何处理，为什么不足。

以下章节缺失时，一般不应直接创建正式方案，除非用户明确接受先生成草稿并把缺失项写入问题文档：

- 背景故事
- 业务目标和技术目标
- 方案总览和核心路径图
- 详细设计
- 模块拆分与配置设计
- 接口与存储
- 关键技术决策 Q&A
- 稳定性与安全 Q&A
- 测试用例与上线方案
- 容量评估

## 阻塞判定规则

命中以下任一情况时，审批结论必须是 `暂不通过`：

- 项目背景缺失，或无法说明业务上下文、现状问题、触发原因、目标用户或影响范围。
- 核心方案链路不清，无法判断主要模块、调用方向、关键数据流或核心接口边界。
- 具体方案只有目标、原则或泛化描述，没有说明具体实现步骤、数据读写、模块调用、异常处理、观测和回滚。
- 方案涉及新接口，但没有基于仓库现有接口风格确定命名、请求/响应结构、错误码、鉴权和测试方式。
- 方案涉及代码改动，但“四、详细设计”的每个具体实现点内没有给出目标文件、目标函数/方法/配置项、插入位置、核心分支、数据读写、异常处理、兼容逻辑或伪代码。
- 方案发生在本地代码仓库中，但每个具体实现点内没有标注代码证据，或具体文件名、函数名、配置 key、错误码、测试位置无法追溯到本地代码读取/subagent 事实输出/用户明确提供的代码事实。
- 方案发生在本地代码仓库中或涉及代码改动，但最终创建文档前没有经过程序员落地性复核，复核结论仍存在阻塞项，或复核给出的可确定修正、建议伪代码、Mermaid 图没有落实到技术方案正文对应实现点。
- 安全鉴权、权限边界、敏感数据处理、加密或审计方案缺失，且方案涉及用户数据、业务敏感数据或跨系统访问。
- 容量、性能、调用链流量、资源水位或压测依据缺失，且方案可能引入新增流量、批量任务、热点资源或核心链路变更。
- 上线方案、灰度策略、回滚方案或故障止损方案缺失，且方案涉及线上变更。
- 对上游或下游存在兼容性风险，但没有迁移、兼容、通知或回滚设计。
- 数据一致性、幂等、事务边界、补偿或历史数据处理缺失，且方案包含写入、迁移、异步处理或多系统同步。
- 监控告警、核心指标或异常定位手段缺失，导致上线后无法判断效果或发现故障。

非阻塞但必须进入问题文档的情况：

- 非核心章节信息不足，但不影响当前方案主链路判断。
- 文档表达不够清晰，但技术路径和风险控制可判断。
- Mermaid 图信息不足，但核心调用链已用文字说明清楚。
- 需要业务方补充验收标准、测试样例或排期细节。
- 个别实现细节尚不确定，但不影响主链路判断，且已按确认问题流程列出待确认选择题。
