# 技术方案评审 Rubric

## 事实输入

评审前提取并区分：

- 产品事实：用户、场景、目标、非目标、验收口径。
- 仓库事实：入口、调用链、数据结构、协议源、配置、测试、当前错误语义。
- 修改点事实：当前 commit、精确文件、完整符号、变量名与类型、定义/读写位置和值来源。
- 运行事实：流量、容量、延迟、依赖 SLA、灰度范围、上线窗口。
- 待决策项：方案选择、兼容策略、迁移方式、回滚条件。

缺失项不得用通用经验填充；标记为阻塞问题或待验证假设。

## 评审输出

在当前 OpenSpec schema 允许的 artifact 中表达：

1. **结论**：通过、带条件通过、需补充后再评审。
2. **阻塞问题**：影响设计成立、上线安全或验收判断的问题及选项。
3. **证据映射**：scenario、文件/符号/变量、测试三者的双向映射。
4. **风险**：稳定性、一致性、安全、性能、兼容、回滚、观测。
5. **上线验证**：基线、自动化测试、测试环境/灰度、指标和停止条件。

## 核心维度

### 调用链和影响面

- 是否从真实入口追到写入、异步、缓存、RPC/MQ 和返回路径。
- design 是否创建于修改点确认之后，并逐项引用已确认的文件、符号和变量。
- 是否列出直接调用方与被调用方，而非只分析目标函数。
- 是否改变协议、错误码、重试、超时、幂等或降级语义。
- 是否识别跨仓库、跨团队、IDL 和生成物边界。

### 数据与并发

- 写操作是否幂等；重试、乱序、重复和部分失败是否安全。
- 事务边界、缓存一致性、锁/TTL、去重粒度和恢复机制是否明确。
- 数据迁移是否兼容新旧版本并可回滚。

### 容量与主链路

- 主链路是否新增扫描、同步等待、放大查询或外部强依赖。
- QPS、单对象上界、worker、队列和超时是否有依据。
- 是否有界、限流、丢弃、补偿和防日志风暴策略。

### 配置、FG 与发布

- 配置中心的空间、key、region、默认值、热更新和错误配置行为是否明确。
- FG 的主体、规则、默认态和关闭后的残留行为是否明确。
- 是否从代码上线且能力关闭开始灰度；每一步是否有观测门槛和独立回滚。

### 安全与权限

- 是否新增外部入口、跨租户访问、敏感数据或高成本操作。
- 鉴权、审计、输入约束和资源滥用防护是否完整。

### 可观测性

- 指标能否区分未触发、未消费、执行失败、执行成功但无效果。
- 日志是否包含必要定位维度且避免泄露或风暴。
- 告警阈值、看板和回滚信号是否可操作。

### 测试可行性

- 是否能用现有测试框架证明修改前后行为，而不是只验证函数被调用。
- 是否覆盖正常、边界、异常依赖、并发、兼容、配置和回滚。
- mock 是否在正确边界，是否误把生成代码或不稳定实现细节当断言目标。

## 阻塞追问

- 哪一条仓库证据证明应修改这个符号？
- 哪个 scenario 会因这处改动通过，哪个既有行为必须保持？
- 如果方案判断错误，最小爆炸半径和最快回滚路径是什么？
- IDL/配置/数据的所有权在哪里，生成或发布顺序是什么？
- 基线失败如何与本次回归区分？
- 测试环境、远程单测、CI 和线上指标分别证明什么，哪些仍无法证明？
