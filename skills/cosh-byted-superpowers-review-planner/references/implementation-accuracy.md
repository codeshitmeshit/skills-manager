# 仓库实现准确性门禁

## 证据等级

按强到弱使用证据：

1. 当前仓库可执行测试、编译结果和实际运行结果。
2. 源代码、协议源文件、配置定义和当前项目指令。
3. 同模块现有调用方与测试惯例。
4. 已确认的原生 Superpowers 规格。
5. 命名、相似项目或通用框架经验。

弱证据不得覆盖强证据。索引、生成产物和历史文档只用于发现候选位置，结论必须回到当前 commit 的源文件验证。

## 实施位置证据卡

编码前为每个实施位置回答：

- 对应哪个规格场景和设计决策？
- 仓库与基线 commit 是什么？
- 精确文件、完整符号、变量名和静态类型是什么？
- 变量在哪里定义、赋值、读取和跨函数传递？
- 当前值来自哪里，目标行为改变什么？
- 哪些邻近逻辑、接口和生成产物不得修改？
- 哪个测试能证明修改前行为与修改后结果？

任一关键答案缺失时先补取证，不得把推测写入规格、计划或代码。

## 源文件与生成边界

- 先查找仓库指令和生成入口，再判断文件所有权。
- 不直接修改 `gen`、`kitex_gen`、protobuf/thrift 生成目录、客户端 SDK、mock 生成物或编译产物。
- 修改协议源、schema 或生成配置后，使用仓库规定的生成方式更新产物。
- 无法确定生成方式或所有权时停止，不以手工同步多个生成文件代替。

## 实现与验证

1. 先记录修改前行为和最小复现或基线测试。
2. 只实现已确认 task 的最小变更，不做无关重构。
3. 修改后检查 diff，排除格式化扩散、调试代码和用户已有变更。
4. 从定点测试逐步扩大到受影响模块测试。
5. 失败时区分基线失败、环境问题和本次回归，并保留证据。
