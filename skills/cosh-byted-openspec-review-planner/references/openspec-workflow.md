# OpenSpec 工作流依据

## 信息源优先级

按以下顺序确定规则，低优先级内容不得覆盖高优先级内容：

1. 当前项目安装生成的 OpenSpec skills、commands 和 schema。
2. OpenSpec 当前版本的官方文档与官方仓库。
3. 当前项目 `openspec/` 配置、自定义 schema 和已有 artifacts。
4. 本 skill 的技术评审与实现准确性规则。
5. 本 skill 的示例；示例不是权威格式。

发生冲突时停止，说明冲突来源及采用高优先级规则的影响。

## 运行时发现

1. 读取项目级 agent 指令和 OpenSpec 相关配置。
2. 检查实际安装版本、可用 skills、commands、schema 和 change 状态，不假设版本专属命令存在。
3. 优先使用项目实际提供的 OpenSpec 能力；缺失时才查官方当前文档。
4. 推进前后都重新读取状态，不解析或维护平行状态文件。
5. 已有自定义 schema 或 artifacts 时不得自动覆盖、重建或降级。

安装、初始化、刷新、schema 读取或状态读取失败时立即停止。若缺少安装或初始化，先告知用户将产生的动作和文件，再按官方当前流程处理。

## Artifact 推进

- 以当前 schema 决定 artifact 名称、依赖和合法顺序。
- 规格必须包含可验证 scenario、边界、失败行为和非目标。
- requirements/scenarios 确认后，先完成 CodeGraph 与源码分析并确认修改点，再创建 design。
- design 中只记录已确认修改点支持的现状和目标决策；不得先写 design 再反向寻找代码证据。
- design 必须引用修改点的文件、完整符号、变量、类型和读写关系；假设必须在创建 design 前消除。
- tasks 必须能追溯到 scenario，并包含预期符号、最小范围、验证和回滚信息。
- 项目 schema 没有对应字段时，将信息写入其允许的描述区域，不额外创建事实状态文件。

## Task 状态更新

单独推进模式的 task 顺序：

1. 读取状态和目标代码。
2. 报告范围与证据。
3. 实现最小变更。
4. 运行最小充分验证并检查 diff。
5. 展示 CR 材料，等待用户 CR。
6. 用户点击网站“推进下一个任务”，或用自然语言明确表示 CR 通过并要求提交、推进。两条路径都重新读取 OpenSpec 并校验当前 task，然后提交整个 Git 暂存区；不得执行 `git add`，暂存区为空时跳过 commit，commit 或 hook 失败时保持未放行。
7. 暂存区 commit 成功或确认无需提交后，记录当前 task CR 通过及推进授权；再更新对应 OpenSpec task 状态，进入下一 task。

页面不是唯一控制入口。自然语言控制必须更新与页面相同的 `cosh-dashboard-control` 元数据，已打开的网站据此实时同步。开始实现前，“继续”“开始实现”“按计划执行”只授权当前 task；展示 CR 材料并等待确认后，上下文明确的“继续”与 `advance-next` 相同，只放行一个 task。用户明确要求“连续推进剩余任务”时写入 `mode=continuous`，明确要求“切回单独推进”时写入 `mode=single`。连续模式保持 task 级测试、自检、提交和状态更新边界，但不等待逐 task 人工 CR。任何失败、规格变化或安全风险仍立即停止。

## 变化、验证与归档

- 需求变化时立即暂停代码，先更新 artifacts 并重走受影响门禁。
- 使用当前版本的 OpenSpec 验证能力检查 artifacts、任务完成度和规格场景。
- 展示 OpenSpec 验证结果、测试命令、实际结果和未覆盖项。
- 测试结果确认后仍需单独等待最终归档确认。
- 最终确认后才归档，并在归档后重新读取状态。
