# 通用代码编写规范

## 优先级

按以下顺序选择实现：

1. 直接复用当前模块已有函数、类型、组件、配置和测试工具。
2. 在不改变既有语义与依赖方向的前提下，小幅扩展已有能力。
3. 组合仓库内已经稳定使用的底层能力。
4. 只有以上方案都无法安全满足已确认 scenario 时，才新增函数、类型、抽象或模块。

不得仅因现有接口“不够漂亮”而复制实现或重写基础设施。决定新增时，在 task 或 CR 材料中写明已检查的复用候选、不能复用的具体原因、最小新增边界和后续所有者。

## 简洁实现

- 选择满足规格的最小改动，避免无关重构、提前抽象、猜测性兼容和未被 scenario 驱动的配置项。
- 优先清晰的数据流、短小职责和已有惯例；减少不必要的层级、包装、分支和状态。
- 简洁不等于压缩代码。不得用晦涩表达式、隐式副作用或删除必要校验来减少行数。
- 新增公共能力前检查重复实现；确需公共抽象时保持单一职责和稳定依赖方向。
- 不修改生成产物、第三方代码、许可证文本或与当前 task 无关的历史代码。

## 中文注释

新增或修改的核心业务逻辑必须添加对应中文注释，重点解释：

- 为什么需要该逻辑以及对应的业务 scenario；
- 容易误解的边界、保持不变的行为和失败语义；
- 并发、幂等、缓存、降级、兼容或回滚约束；
- 无法直接复用既有能力时采用当前实现的原因。

注释应放在最接近被解释逻辑的位置。不要逐行翻译代码、复述变量名、保留失效 TODO，或用注释掩盖过度复杂的实现。语言或仓库对导出 API 注释有固定格式时，在满足格式的同时使用中文说明其业务语义。生成文件和第三方文件不补手工注释。

## 日志与可观测性

- 复用项目现有日志框架、上下文和结构化字段，不引入第二套 logger。
- 在关键入口、重要分支、状态变化、降级/重试和失败路径提供必要日志；正常热路径只在确有诊断价值时记录。
- 日志至少包含能关联请求和业务对象的安全字段，例如 trace/request ID、稳定对象 ID、动作、结果和错误类别；沿用仓库字段命名。
- 使用符合项目惯例的日志级别。预期内分支不得滥用 error，真正失败不得只记 debug。
- 同一错误在合适的责任边界记录一次，避免每层重复打印；循环、重试和高 QPS 路径必须考虑采样、聚合或限频。
- 禁止记录密码、令牌、密钥、完整请求体、个人敏感信息或未经脱敏的业务数据；高基数字段不得直接成为指标标签。
- 日志不能代替错误处理、指标或测试。对关键日志分支，尽量用现有测试能力验证级别、字段或触发条件。

## CR 检查

提交 CR 材料前逐项确认：

- 是否复用了仓库已有能力，是否存在重复实现？
- 新增抽象是否确有必要，边界是否最小？
- 核心逻辑是否有解释原因和边界的中文注释？
- 关键成功、分支和失败路径是否可观测？
- 日志是否可定位、已脱敏、不过量且不会形成日志风暴？
- diff 是否仍只覆盖当前 OpenSpec task？
