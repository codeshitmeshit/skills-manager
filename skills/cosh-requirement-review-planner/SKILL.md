# OpenSpec 需求方案评审与完整研发流程

## 目标

将已澄清需求转成可验证的 OpenSpec artifacts。先用 CodeGraph 和源码读懂当前实现并锁定修改点，再围绕修改点创建 design；让每一处代码修改都同时有规格依据和仓库事实依据。宁可暂停补证据，不凭文件名、经验或方案文字猜实现。

## 必读资源

- 开始任何阶段前完整读取 [`references/openspec-workflow.md`](references/openspec-workflow.md)。
- 技术评审前完整读取 [`references/technical-review-rubric.md`](references/technical-review-rubric.md)。
- 进入仓库分析、任务拆分或编码前完整读取 [`references/implementation-accuracy.md`](references/implementation-accuracy.md)。
- 生成 tasks、编码或 CR 前完整读取 [`references/code-authoring-standards.md`](references/code-authoring-standards.md)。
- 使用 CodeGraph、确认修改点或创建 design 前完整读取 [`references/codegraph-modification-point.md`](references/codegraph-modification-point.md)。
- 创建、启动或解释实时进度网站前完整读取 [`references/realtime-dashboard.md`](references/realtime-dashboard.md)。

## 不可变规则

- OpenSpec 是规格、设计、任务、验证和归档的唯一主状态，不创建平行状态机。
- 所有代码、IDL、配置、脚本和测试变更都必须追溯到已确认的 OpenSpec scenario 或 task。
- 先读取仓库根目录到目标文件路径上的 `AGENTS.md`，再执行仓库操作。
- 只修改源文件；遇到 Thrift、Protobuf、OpenAPI、mock 或其他生成产物时，先定位生成源和仓库规定的生成方式。
- design 必须后于 CodeGraph 分析和修改点确认；禁止先写 design，再反向寻找代码支持方案。
- 修改点必须精确到仓库、文件、符号和变量，说明变量类型、定义、读写位置、值来源及预期变化；只知道模块或函数名不算定位完成。
- CodeGraph 负责发现代码实体、调用路径和影响面；变量级结论必须回到当前 commit 的源码定点阅读确认。
- 未取得“规格事实 + 仓库事实”双重证据时，不得把推测写进 design、tasks 或代码。
- 编码时优先复用仓库已有能力并保持最小、简洁的实现；只有现有能力无法在正确边界内安全复用时才新增抽象、函数或模块，并记录不能复用的证据。
- 新增或修改的核心业务逻辑必须有说明意图、边界或原因的中文注释；关键分支、状态变化和失败路径必须复用项目日志体系提供可观测性，同时禁止敏感信息泄露、重复报错和日志风暴。
- OpenSpec 安装、状态读取、schema 或 artifact 校验失败时停止，不降级为对话中的临时计划。
- 实时网站除受控执行授权外只读消费 OpenSpec；页面和自然语言是等价控制入口，共用当前 tasks artifact 的 `cosh-dashboard-control` 元数据记录推进模式和 CR 放行。推进下一任务前必须校验当前 task 并处理 Git 暂存区。不得自动暂存文件或创建空提交；不修改 checkbox、规格、design 或代码，也不生成平行状态文件。
- 不假设某个 CodeGraph 或外部研发工具必然可用；先发现当前仓库与环境实际能力。工具不可用时使用本地源码、仓库检索、语言服务或项目原生工具完成同等证据，不得伪造结果。

## 人工确认门禁

以下节点分别等待明确确认，不合并、不推断：

1. **规格确认**：proposal、requirements、scenarios 与非目标准确。
2. **修改点确认**：CodeGraph 调用链与源码变量流已核实，修改位置唯一且边界清晰。
3. **技术方案确认**：基于已确认修改点创建的 design、影响、取舍和风险成立。
4. **任务清单确认**：tasks 可独立实现、验证并追溯到规格。
5. **任务 CR 与提交确认**：单独推进模式下，每个 task 的 diff 和测试证据通过 CR 后，由用户点击“推进下一个任务”或用自然语言明确要求提交并推进；连续推进模式以用户在页面或自然语言选择该模式作为剩余 tasks 的批量授权。
6. **测试结果确认**：OpenSpec 验证、自动化测试和必要环境验证满足规格。
7. **最终归档确认**：确认可闭环后才归档。

开始编码前，普通的“继续”“开始实现”“执行吧”只授权当前一个 task。展示当前 task 的 CR 材料并明确等待 CR 后，用户说“CR 没问题，推进下一个任务”“提交当前任务并继续”或上下文明确的“继续”，等价于页面的 `advance-next`；不得把它解释为批量授权。只有用户明确要求“连续推进剩余任务”，或控制元数据已记录 `mode=continuous`，才允许连续执行；最终测试和归档确认仍不可跳过。

## 工作流

### 1. 确认输入

1. 判断目标、用户场景、范围、非目标、约束和验收标准是否清楚。
2. 未澄清时使用 `cosh-product-clarifier`；已澄清时输出需求摘要并等待确认。
3. 识别目标仓库、模块、服务和预期交付形式；缺失但可从工作区发现时先只读查找。

### 2. 发现 OpenSpec 运行时

1. 按 `openspec-workflow.md` 发现当前项目实际安装、skills、commands、schema、配置和 change 状态。
2. 使用实际 schema 创建或继续 change；不得硬编码某一版本命令或 artifact 模板。
3. 写入可验证的 requirements、scenarios、边界和非目标，完成后等待**规格确认**。
4. change 可读取后，按 `realtime-dashboard.md` 启动实时进度与任务控制网站；输出本地访问地址，并保持服务贯穿后续阶段。

### 3. 使用 CodeGraph 分析代码

1. 检查工作树状态，只读识别用户已有修改，不覆盖或混入无关变更。
2. 优先使用当前环境可用的 CodeGraph、语言服务或代码索引定位候选接口、代码实体、上游、下游和调用图；调用任何工具前先查看实际帮助或 schema，不得猜参数或枚举。
3. 已知实体时优先精确查询；未知时先语义检索候选，再逐步收敛，不把第一个结果直接当修改点。
4. 用本地 `rg --files`、`rg` 和定点阅读复核 CodeGraph 结果，确认当前 commit 中的入口、调用方、实现、数据结构、配置、测试和生成边界。
5. 对接口定义优先使用仓库原生协议定位、代码生成或 schema 工具，不得直接搜索后修改生成代码。
6. 沿数据流识别候选变量：定义位置、静态类型、赋值来源、读取点、写入点、跨函数传递和生命周期。
7. 运行最小基线测试或静态检查，确认修改前行为；无法运行时记录原因和替代证据。

### 4. 确认修改点

1. 按 `codegraph-modification-point.md` 生成修改点卡片，至少包含：仓库与 commit、文件路径、完整符号、变量名与类型、定义/读写位置、当前值来源、预期变化、上下游影响、测试锚点和排除的替代点。
2. 选择能满足 scenario 的最小修改点；不能仅写“修改某模块”“调整某函数逻辑”或“增加一个变量”。
3. 一个修改点对应一个清晰 design 决策。确需多个修改点时逐点建卡，说明依赖顺序，不合并成笼统修改范围。
4. CodeGraph 与本地源码不一致时以当前 commit 源码为准，并标记索引可能过期；未完成源码复核时停止。
5. 展示修改点卡片和未决假设，等待**修改点确认**。确认前不得创建或填写 design。

### 5. 基于修改点创建并评审 design

1. 只基于已确认修改点创建 OpenSpec design，不在 design 阶段重新猜测实现位置。
2. 在 design 中逐项引用修改点卡片的文件、符号、变量和数据流事实，并说明变量从什么值变成什么行为。
3. 按 `technical-review-rubric.md` 检查架构、协议、数据、权限、状态流、异常、兼容、迁移、性能、安全、可观测性、灰度和回滚。
4. 对每个修改点建立双向映射：`scenario -> 文件/符号/变量 -> 测试`，同时检查每个拟改文件和变量是否有对应 scenario。
5. 明确最小改动边界、保持不变的变量与行为、失败语义和上下游兼容条件。
6. 按 `realtime-dashboard.md` 将评审当前阶段、未通过结论、证据、精确修改位置和可执行修改建议持续写回 OpenSpec artifacts；结论或阶段变化时立即更新，不能等整轮结束后一次性补写。阻塞问题未解决时停止。
7. 展示 design 与修改点的逐项对应关系，等待**技术方案确认**。

### 6. 生成可执行 tasks

1. 按可独立 CR、提交、回滚和验证的边界拆分 task，不按文件数量机械拆分。
2. 每个编码 task 必须写明：对应 scenario 和 design 决策、修改点卡片、精确文件/符号/变量、优先复用的现有能力、确需新增时的理由、中文注释位置、日志观测点、不得修改项、实现步骤、验证命令和回滚方式。
3. IDL、生成代码、配置、数据迁移和跨仓库依赖必须拆出正确顺序和所有权。
4. 测试与文档不能仅作为最后一个笼统 task；把验证放入对应实现 task。
5. 等待**任务清单确认**。

### 7. 编码前复核

每个 task 开始前重新读取 OpenSpec 状态和目标代码，并报告：

- task 编号及对应 scenario；
- 当前调用链和基线行为；
- 预计修改的精确文件、符号、变量、读写位置与原因；
- 明确不改的邻近逻辑；
- 本轮测试命令与失败时停止条件。

若代码自评与已确认 design 不一致，先更新 OpenSpec 并重新走受影响门禁，不得边写边修正规格。

### 8. 实现一个 task

1. 每次开始前读取 tasks artifact 中的执行控制元数据；缺失或无效时默认为**单独推进**。
2. 先补能证明需求或复现缺陷的测试；不适合测试先行时说明原因，再做最小实现。
3. 先复用已确认的现有函数、类型、组件和基础设施；确认复用会破坏语义、依赖边界或可维护性时才做最小新增，不做无关重构、顺手清理或猜测性兼容。
4. 为新增或修改的核心业务逻辑补充中文注释，并在关键分支、状态变化和失败路径使用项目现有日志框架增加必要观测；注释解释原因和边界，日志包含可定位字段且不得泄露敏感信息。
5. 修改后立即检查 diff，确认实现简洁、没有重复能力、生成物误改、调试代码、无关格式化或用户变更被覆盖。
6. 运行从定点测试到受影响模块测试的最小充分验证；需要远程执行时使用当前环境实际提供的远程测试能力。
7. **单独推进**：展示 diff、验证证据、风险和未验证项后暂停；用户完成 CR 并通过页面或自然语言要求推进后，先重新读取 OpenSpec，校验 change、tasks 版本和当前 task，再检查并提交整个 Git 暂存区。不得执行 `git add`；暂存区为空时不创建空提交；commit 或 hook 失败时不得记录放行。成功后在同一 `cosh-dashboard-control` 元数据中记录当前 task CR 通过及提交授权，并记录下一 task，更新当前 task 后再进入下一 task。
8. **连续推进**：把用户通过页面或自然语言选择此模式视为对剩余 tasks 的批量授权，并将 `mode=continuous` 写入同一控制元数据；每个 task 仍分别完成测试、Codex 自检、commit 和 OpenSpec 状态更新，但不等待人工 CR 或“推进下一个任务”。用户说“切回单独推进”时写入 `mode=single`，完成当前 task 后恢复逐项等待。
9. CR 修改、测试失败、规格变化、修改点失效、无法独立提交或安全风险在两种模式下都必须停止；连续推进不得越过这些异常。
10. 连续推进完成所有 tasks 后停止，展示汇总 diff、commits 和验证证据，等待**测试结果确认**。

### 9. 环境验证与交付

- 使用当前仓库实际的配置、Feature Gate、测试环境、日志、代码评审和 CI 工具完成验证；部署前确认分支、环境、依赖、验证用例、灰度和回滚。
- 工具结果必须回填为 OpenSpec 验证证据，不用“已调用工具”代替结果判断。
- 等待**测试结果确认**，再等待**最终归档确认**；确认后才归档并复查实际状态。
- 每次 OpenSpec artifact 或 task 状态变化后确认网站已自动反映；页面状态与 OpenSpec 不一致时以 OpenSpec 为准并修复读取适配，不手工改页面数据。

## 实时进度网站

- 网站是实时观察与可选控制界面，不是执行流程的前置条件或唯一入口。用户完全不操作页面时，仍可用自然语言推进当前 task、在 CR 后提交并推进、切换连续/单独模式；所有操作必须复用页面相同的校验、提交规则和 `cosh-dashboard-control` 元数据，使已打开页面通过 SSE 自动同步。
- 使用 [`scripts/serve_openspec_dashboard.py`](scripts/serve_openspec_dashboard.py) 读取目标项目，使用 [`assets/dashboard/`](assets/dashboard/) 渲染页面。
- 默认绑定 `127.0.0.1`，只在用户明确要求共享且确认安全边界后才改变监听地址。
- 页面展示 change、当前阶段、总体进度、七个人工门禁、修改点卡片、design、评审实时阶段、未通过结论及修改方式、task 完成度、测试证据、风险和最后更新时间。
- 一个服务实例扫描项目内全部活动 change；页面顶部提供 Change 切换器，并将选择写入 URL。状态流、文件读取和控制请求必须显式绑定所选 change，禁止跨 change 复用状态或写错 tasks artifact。
- 总览与详情页提供产物导航；只显示实际存在的类型，点击后在统一只读页面查看全部同类文件。把 Tasks 固定为最右侧入口，并使用区别于普通产物的高识别度颜色，突出其开发主入口地位。
- 多个修改点分别提供独立 URL；修改点详情页用“规格、Design、Tasks、验证、代码证据”标签按需展示对应 OpenSpec 文件。
- 总览页只展示 task 总体进度；完整任务列表只放在顶部导航的 Tasks 产物页。把“连续推进 / 单独推进”放在 Tasks 页顶部；单独推进时用“推进下一个任务”按钮替换当前任务行右侧的状态文字，不增加底部控制区，连续推进时完全移除该按钮。Tasks 页不重复展示原始 `tasks.md` 阅读器。控制请求必须绑定当前任务。
- 页面或自然语言产生的模式和 CR 放行都写入 tasks artifact 的受控注释元数据；使用版本校验防止覆盖 agent 或用户刚更新的 tasks。“推进下一个任务”只提交已经暂存的内容，不执行自动 `git add`。
- 通过 Server-Sent Events 推送实时状态；OpenSpec 文件变化后无需刷新页面、重新生成页面或重启服务。
- 服务启动后持续监听 artifact 新增、删除、正文、checkbox、修改点、控制授权和验证证据变化，不能只在阶段切换时刷新。
- 找不到 change、artifact 无法解析或读取结果过期时显示明确错误，不用缓存成功页面冒充实时状态。
- 启动命令、字段映射和验证方式以 `realtime-dashboard.md` 为准。

## 需求变化与阻塞

- 编码后出现新增、删除或语义变化时立即暂停，先更新 OpenSpec，再重新确认受影响的规格、design 和 tasks。
- 修改点在实现时失效、变量不存在、类型或读写关系变化时立即暂停，重新运行 CodeGraph 与源码分析，并重新确认修改点和 design。
- 发现调用链、IDL 所有权、配置归属、生成方式或测试基线与方案不符时立即暂停，不猜测修补。
- 当前 task 无法独立验证或提交时说明依赖，等待用户决定是否调整 task，不自行扩大范围。
- 测试失败必须先判断是基线失败、环境问题还是本次回归；无证据不得宣称与本次无关。

## 输出规则

- 每次交付包含：change、状态、已读信息源、证据、更新 artifacts、验证结果、未决风险和下一门禁。
- 每次阶段交付同时给出实时网站地址和页面最后更新时间；服务不可用时明确说明，不宣称页面正在实时更新。
- 技术结论必须区分“已证实”“合理推断”“待确认”；代码只允许依赖已证实事实和已确认决策。
- 修改点必须精确输出文件路径、完整符号、变量名、类型、定义和读写行；验证命令必须可复查。
- 不把 skill 示例、历史方案或生成代码当作当前仓库事实。

## 质量检查

- OpenSpec 仍是唯一主状态，且所有变更可追溯到 scenario/task。
- CodeGraph 分析先于修改点确认，修改点确认先于 design 创建。
- 每个修改点都有仓库、commit、文件、符号、变量、读写关系、影响面和测试锚点。
- 每个实现 task 都有已确认修改点、仓库证据、最小范围、不得修改项和验证命令。
- 已证明优先复用现有能力；所有新增抽象都有必要性证据，核心逻辑具备有效中文注释，关键路径具备安全且不过量的日志观测。
- 已确认调用链、接口源文件和生成边界，没有凭名称猜实现。
- 修改前基线、修改后定点测试和受影响范围验证均有证据或明确未验证原因。
