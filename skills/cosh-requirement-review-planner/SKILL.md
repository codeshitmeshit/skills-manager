# OpenSpec 需求方案评审与执行规划

## 目标

在产品需求澄清后，以 OpenSpec 驱动需求规格、技术设计、任务、实现、验证和归档，并通过人工确认门禁确保实现始终服从已确认规格。

## 核心原则

- OpenSpec 是唯一主状态，也是规格、设计、任务、验证和归档的主要信息源。
- 所有代码变更都必须进入 OpenSpec，包括小修复、配置修改、新功能和重构；不得绕过 OpenSpec 直接编码。
- 本 skill 只增加产品澄清衔接、技术评审和人工确认门禁，不创建、镜像或双写平行状态机。
- 执行前必须完整读取 [`references/openspec-workflow.md`](references/openspec-workflow.md)，按其中的信息源优先级和运行时发现规则操作。
- OpenSpec 安装、初始化、状态读取或 artifact 校验失败时停止，不得降级使用旧流程。

## 人工确认门禁

以下五个节点必须分别等待用户明确确认，不得合并确认或自动跳过：

1. **规格确认**：确认需求 proposal、requirements 和 scenarios 准确表达需求。
2. **技术方案确认**：确认 design、关键取舍、风险和兼容性处理。
3. **任务清单确认**：确认 tasks 覆盖实现、测试和必要文档工作。
4. **测试结果确认**：确认 OpenSpec 验证结果和关联测试证据满足规格。
5. **最终归档确认**：确认需求可闭环后才执行 OpenSpec 归档。

确认必须来自用户的明确表达。沉默、继续执行指令之外的推测或 agent 自评不得视为确认。

## 任务级实现门禁

- 默认一次只实现一个尚未完成的 OpenSpec task。任务数量、实现难度和任务间依赖不能成为自动批量执行的理由。
- “继续”“开始实现”“按计划执行”“执行吧”等普通推进指令只授权当前一个任务，不能视为批量授权。
- 只有用户明确授权“一次全部实现”“批量实现”“连续完成这些任务”或其他含义等价的指令时，才允许在该次授权范围内连续实现多个任务。
- 批量授权不得自行推断；授权范围不明确时仍按单任务执行。
- 每个任务开始前，报告 task 编号、目标、预计修改文件和本轮验证方式。
- 每个任务实现后，只运行与该任务相关的最小充分验证，并展示变更文件、diff 摘要、验证证据、风险和未验证项，然后等待用户 CR。
- 用户提出 CR 修改意见时，不得 commit；完成修改和验证后必须重新等待用户 CR。
- 只有用户明确表示 CR 通过并明确同意提交后，才允许为当前任务创建 commit。
- commit 成功后才能更新对应 OpenSpec task 状态；随后必须停止并等待用户确认继续下一个任务。
- 未获得下一任务确认前，不得预先修改下一任务涉及的文件。批量授权场景除外，但仍应按 task 边界验证、提交和更新状态。

## 工作流

1. 判断产品需求是否已经澄清。
   - 产品目标、用户场景、范围、非目标或成功标准仍不明确时，必须使用 `cosh-product-clarifier` 继续澄清。
   - 产品澄清完成前，不进入 OpenSpec change 创建或技术评审。
2. 整理需求总结并等待用户确认。
   - 总结背景、目标用户、目标、范围、非目标、关键约束和验收意图。
   - 只有用户确认总结后，才开始准备 OpenSpec。
3. 准备并读取 OpenSpec。
   - 按 `references/openspec-workflow.md` 检查安装、初始化、项目配置、schema、skills、commands 和当前状态。
   - 缺少 OpenSpec 时先告知用户，再执行官方当前流程要求的安装和初始化。
4. 创建或继续 OpenSpec change。
   - 使用当前项目实际提供的 OpenSpec skill 或 command，不硬编码特定版本命令。
   - 按当前 schema 创建或更新需求 artifacts，并等待**规格确认**。
5. 评审技术方案。
   - 评审前完整读取 [`references/technical-review-rubric.md`](references/technical-review-rubric.md)。
   - 检查架构、接口、数据、权限、状态流、异常、兼容性、迁移、性能、安全、可观测性和测试可行性。
   - 评审意见必须推动 OpenSpec proposal、specs 或 design 修订，不另建事实来源。
   - 存在阻塞问题时停止；无阻塞问题后等待**技术方案确认**。
6. 生成或更新 OpenSpec tasks。
   - tasks 必须覆盖实现、测试、验证和必要文档，并能追溯到已确认规格。
   - 等待**任务清单确认**；确认前不得进入编码。
7. 执行实现。
   - 使用当前项目实际提供的 OpenSpec apply/implementation 能力选择一个尚未完成的 task。
   - 每次编码前重新读取 OpenSpec 状态；只实现当前 task 和已确认 artifacts 中的内容。
   - 严格执行“任务级实现门禁”：实现、最小验证、等待用户 CR、获得提交确认、commit、更新 task 状态。
   - commit 成功后停止，等待用户确认继续下一个任务；不得因为 tasks 已整体确认就连续执行剩余任务。
8. 验证实现。
   - 使用当前版本提供的 OpenSpec 验证能力检查 artifacts、任务和规格场景。
   - 执行相关自动化测试和人工验证，展示命令、结果摘要、失败项与未覆盖项。
   - 等待**测试结果确认**。
9. 归档。
   - 测试结果确认后，继续等待**最终归档确认**。
   - 最终确认后才使用当前版本提供的 OpenSpec 归档能力，并报告归档后的实际状态。

## 规格变化

编码开始后，只要用户提出任何新增、删除或变化要求，必须立即暂停编码：

1. 使用 OpenSpec workflow 更新需求规格。
2. 等待用户重新确认规格。
3. 检查技术方案、任务清单和验证场景是否受影响。
4. 更新所有受影响 artifacts，并重新执行对应确认门禁。
5. 受影响阶段全部重新确认后才恢复编码。

不得先完成实现再补规格，也不得只在对话或评审备注中记录变化而不更新 OpenSpec。

## 旧需求兼容

- 旧需求资料只可作为迁移输入，不可继续作为主状态。
- 恢复旧需求时，先将仍然有效的需求、方案、任务和验证信息迁入一个 OpenSpec change，并等待对应确认。
- 迁移完成后只推进 OpenSpec，不双写旧状态文件。
- 历史资料与 OpenSpec 冲突时，停止并让用户确认采用哪项业务事实；状态和 artifact 结构仍以 OpenSpec 为准。

## 阻塞规则

遇到以下情况必须停止，不得猜测或绕过：

- 产品需求尚未澄清或需求总结尚未确认。
- OpenSpec 安装、初始化、刷新或状态读取失败。
- 当前项目 schema、配置或 artifacts 冲突、损坏或无法验证。
- 技术评审存在阻塞问题。
- 任一人工确认门禁尚未完成。
- 当前 task 尚未通过 CR、尚未获得提交确认，或 commit 后尚未获得继续下一个任务的确认。
- 实现、测试或文档与已确认规格不一致。

## 输出规则

- 每次交付说明当前 OpenSpec change、实际状态、已读取的信息源、已更新 artifacts 和下一步门禁。
- 评审意见应指出需要修改的 OpenSpec artifact 和原因。
- 验证结果必须包含可复查的命令或操作、实际结果和对应规格场景。
- 等待用户确认时明确指出确认对象，且不提前执行下一阶段动作。
- 不把 skill 内示例当作项目实际 schema；artifact 格式始终服从当前项目 OpenSpec。

## 质量检查

交付前确认：

- 当前状态来自 OpenSpec，未创建平行状态机。
- 所有代码变更均已进入 OpenSpec。
- 已读取当前项目实际的 OpenSpec skills、commands、schema、配置和 artifact 状态。
- 五个人工确认门禁均未跳过。
- 未获得明确批量授权时，每次只实现了一个 task，并在 CR、提交和继续确认处停止。
- 技术评审意见已经反映到 OpenSpec artifacts。
- 规格变化后已暂停实现，并重新确认所有受影响阶段。
- 实现与已确认规格一致。
- 验证结果包含规格场景、任务完成度和测试证据。
- 归档前已经完成测试结果确认和最终归档确认。
