# 项目逆向拆解与 HTML 教程

## 强制前置条件

本 Skill 必须使用 Subagent / 多 Agent 协作能力。主 Agent 不得单独完成全部分析，也不得只用文字模拟多 Agent。

执行任何项目分析或文件写入前，按顺序检查：

1. **Subagent 能力**
   - 存在：启动 Subagent 并行分析。
   - 不存在：提示用户启用或安装 Subagent 能力，并停止。
2. **`cosh-tutorial-html-docs` Skill**
   - 存在：读取该 Skill，并用它创建或更新 HTML 教程站点。
   - 不存在：提示用户安装 `cosh-tutorial-html-docs`，并停止。

缺少 Subagent 时使用提示：

```text
当前环境未检测到 Subagent / 多 Agent 协作能力，无法按本 Skill 要求完成项目逆向拆解。请先启用或安装支持 Subagent 的能力后再继续；在此之前，我不会继续分析项目或生成 HTML 教程。
```

缺少 `cosh-tutorial-html-docs` 时使用提示：

```text
当前环境未检测到 cosh-tutorial-html-docs Skill，无法生成 HTML 教程文档。请先安装该 Skill 后再继续；在安装完成前，我不会继续进行教程生成或文件写入。
```

## 目标

帮助个人开发者快速读懂陌生开源项目，并生成可直接打开阅读的 `.cosh-docs/` 静态 HTML 教程站点。

教程遵循 **7:3 黄金法则**：

- **70% 现状静态拆解**：当前目录、模块边界、入口、核心 Happy Path、关键抽象，以及 3 到 5 条高价值具体执行链路。
- **30% 真实历史演进**：只基于 Git commit、tag、blame、diff 解释主流程和重点链路相关复杂设计的来源。

7:3 是认知重心，不是机械字数比例。无真实 Git 证据时，不得编造演进叙事，必须标注不可验证或要求用户补充历史材料。

## 主 Agent 职责

主 Agent 是协调者、监督者和最终汇总者，负责：

- 检查 Subagent 能力和 `cosh-tutorial-html-docs` 是否可用。
- 分派并行分析任务，控制每个 Subagent 的输入范围。
- 汇总结构、链路、历史三类证据。
- 从粗分析结果中建立 `linkage_inventory`，筛选 3 到 5 条最值得新手深挖的具体执行链路。
- 处理 Subagent 结论冲突，优先保证架构完整性。
- 确保教程主线围绕最核心 Happy Path。
- 汇总各 Subagent 在正文中预留的关键概念下标，筛掉初级开发者默认应掌握的基础词，只保留会阻碍理解当前章节的项目、框架或架构概念。
- 执行质量保障流程：证据矩阵、交叉质询、图表验收和最终风险声明。
- 使用 `cosh-tutorial-html-docs` 将各 Subagent 的 HTML-ready 素材整理成相互独立的教程页面。
- 监督 HTML 教程生成质量和 `.cosh-docs/guide.html` 入口更新。

## Subagent 分工

本流程至少生成 **6 个 HTML 页面**：

1. 总览页：由主 Agent 生成，负责项目定位、核心 Happy Path 摘要、跨页导航和结论对齐。
2. 结构分析相关页面：由结构分析 Subagent 调研后决定页数，至少 1 页。
3. Happy Path 总线页：由链路发现 Subagent 调研后生成，至少 1 页。
4. 具体链路深挖页：由链路深挖 Subagent 基于 `linkage_inventory` 生成，默认 3 到 5 页；项目很小时不得少于 2 页。
5. Git 历史溯源相关页面：由 Git 历史溯源 Subagent 调研后决定页数，至少 1 页。

每个 Subagent 除了基本分析结论以外，必须在调研完成后输出自己的页面计划：建议页面个数、每个页面的文件名、标题、目标读者问题、内容范围、证据来源和与其他页面的边界。主 Agent 汇总页面计划后决定最终页面总数；不得少于 6 页，也不得把某个 Subagent 明确建议拆分的独立主题强行合并。Subagent 各自只负责自己页面计划内的素材，不要跨页代写另一个 Subagent 的正文。

每个 Subagent 在写页面素材时，还必须以初级开发工程师视角记录少量 `concept_candidates`：只收集会影响理解本章节主流程的项目自定义概念、框架关键抽象、架构模式、运行时机制或构建/插件机制术语。不要解释正常计算机基础和初级工程师默认应掌握的词，例如 function、class、module、import、config、request、response、API、JSON、HTTP、CLI。不要把普通英文直译词做成词汇表；manager、helper、utils、service 这类词只有在项目中承担特殊职责时才收集。

### 并行扩展策略

为了节省时间，主 Agent 应尽量增加并行 Subagent，但必须保持职责边界清楚。默认最少使用结构分析、链路发现、链路深挖、Git 历史溯源四类 Subagent；项目较大或用户要求加速时，可以扩展为 8 到 12 个并行 Subagent。

推荐并行扩展：

- **结构分片 Subagent**：按目录、包、应用、服务或插件拆分结构分析；每个 Subagent 只负责自己的边界和依赖方向。
- **链路深挖 Subagent 池**：每条入选重点链路分配一个独立 Subagent；3 到 5 条链路可同时深挖，不要让一个 Subagent 串行写完所有链路。
- **验证调试 Subagent**：专门为 Happy Path 和重点链路寻找最小运行命令、样例输入、断点、日志观察点和失败检查点。
- **图表 Subagent**：专门把结构、主流程、链路、数据流和历史演进转换成图表计划或 SVG/Mermaid 素材，并标注每条边的证据。
- **概念补充 Subagent**：专门汇总各页面 `concept_candidates`，筛掉基础词，生成每页末尾的关键概念补充素材。
- **页面写作 Subagent 池**：在主 Agent 确定页面计划和证据矩阵后，每个详情页可分配一个页面写作 Subagent，把已验证素材整理成 HTML-ready 正文。
- **交叉审阅 Subagent**：并行审阅其他 Subagent 的页面素材，专查缺证据、断链、代码摘录不足、概念过度解释、运行验证不可执行和图表不一致。

并行上限按项目规模调整：

- 小项目：4 到 6 个 Subagent，避免协调成本超过分析收益。
- 中型项目：6 到 10 个 Subagent，优先按链路和页面并行。
- 大型项目：10 到 12 个 Subagent，必须先由主 Agent 明确目录边界、链路边界和页面边界。

并行协作约束：

- 主 Agent 必须先给每个 Subagent 明确输入范围、禁止范围、输出字段和页面边界。
- Subagent 不得跨边界修改另一个 Subagent 的页面正文；发现问题只输出 `review_notes` 或返工建议。
- 页面写作 Subagent 只能使用已验证素材，不得新增无证据结论。
- 图表、概念、验证调试类 Subagent 产出的是页面素材，不单独决定最终页面结构。
- 主 Agent 必须串行完成链路筛选、证据矩阵裁决、冲突处理、质量闸门和最终 HTML 合并。
- 如果 Subagent 结论冲突，不能为了速度直接合并，必须按代码 > 配置 > 测试 > 文档 > Git 历史解释的顺序裁决。

### 结构分析 Subagent

职责：

- 扫描目录树、README、配置文件和模块入口。
- 识别核心目录职责、模块边界、依赖方向和整体架构模式。
- 输出项目全景、目录职能说明和架构图建议。
- 调研完成后给出结构分析相关的 `page_count` 和页面清单；至少包含 1 个结构分析页面，可按项目规模拆分为项目全景、目录地图、模块边界、依赖方向等多个独立页面。
- 为页面清单中的每一页输出完整页面素材，包括文件名、标题、摘要、目标问题、正文范围、项目定位、技术栈、目录地图、核心模块职责、依赖方向、架构图建议、证据清单和延伸阅读。

目标：回答“这个项目由哪些部分组成，各自承担什么角色”。

### 链路发现 Subagent

职责：

- 从启动入口、命令入口、路由入口或任务调度入口出发。
- 追踪最核心的 Happy Path。
- 识别可被新手独立学习的具体执行链路，例如启动链路、配置加载链路、请求路由链路、任务调度链路、Agent 调用链路、文件写入链路、错误处理链路。
- 输出 `linkage_inventory`，每条链路必须包含链路名称、入口、终止点、触发条件、关键模块、是否属于主 Happy Path、证据路径和深挖优先级。
- 给出 Happy Path 总线页的页面素材，包括文件名、标题、摘要、入口定位、主流程骨架、关键函数或类、关键配置、核心抽象、主流程图建议、代码证据和读者提示。

目标：回答“项目最核心的功能是怎么跑起来的”。

### 链路深挖 Subagent

职责：

- 基于主 Agent 确认后的 `linkage_inventory`，逐条拆解 3 到 5 条高价值链路；项目很小时至少拆 2 条。
- 每条链路产出一个独立 HTML 页面素材，不得把多条链路塞进同一个正文页。
- 每条链路必须追到真实代码节点，而不是停在“调用核心模块处理”这类泛称。
- 分析链路中的数据变化、分支条件、异常路径、兜底逻辑和跨模块边界。
- 为每条链路挑选关键代码摘录，代码必须能支撑链路步骤、数据流、分支或终止点说明。
- 为每条链路提供调用链图或时序图计划，并说明每条关键边的证据来源。

目标：回答“这条具体功能链路每一步到底经过哪些代码，数据怎么流动，哪里会分叉或失败”。

### Git 历史溯源 Subagent

职责：

- 基于真实 Git 历史分析主流程和重点链路相关文件。
- 追踪关键 commit、tag、blame 和 diff。
- 解释复杂设计、重构、缓存、状态机、防御性代码的真实引入原因。
- 调研完成后给出 Git 历史溯源相关的 `page_count` 和页面清单；至少包含 1 个历史溯源页面，可按项目规模拆分为历史时间线、关键重构、复杂设计来源、不可验证项等多个独立页面。
- 为页面清单中的每一页输出完整页面素材，包括文件名、标题、摘要、目标问题、正文范围、历史时间线、关键 commit 或 tag、blame 与 diff 摘要、复杂设计引入原因、关联链路、演进图建议、证据引用和不可验证声明。

目标：回答“当前复杂设计为什么会变成现在这样”。

每个 Subagent 都要把结论整理成可被 HTML 教程直接吸收的页面计划和独立页面素材。Subagent 的结果不得互相合并成同一个正文页面，也不得改写成一个割裂的 Agent 报告；主 Agent 只负责交叉校验、补充总览页、合并页面计划和统一生成站点。不要设置独立的 HTML 生成 Subagent；HTML 站点生成由主 Agent 在汇总后统一调用 `cosh-tutorial-html-docs` 完成。

## 工作流

1. **能力检查**
   - 检查 Subagent 能力；不存在则停止。
   - 检查 `cosh-tutorial-html-docs`；不存在则停止。

2. **第一层并行粗分析**
   - 结构分析 Subagent 或结构分片 Subagent 池分析项目全景和模块边界。
   - 链路发现 Subagent 追踪核心 Happy Path 并输出 `linkage_inventory`。
   - Git 历史溯源 Subagent 先定位主流程和候选链路相关关键历史。
   - 验证调试 Subagent 可同步探索最小启动命令、示例输入、测试入口和日志观察点。
   - 每个 Subagent 同步产出页面计划和 HTML-ready 页面素材，而不是只给分析结论。
   - 每个 Subagent 在页面正文素材中为值得解释的概念预留下标，例如 `Adapter[[concept:adapter]]`，并同步输出 `concept_candidates`。下标必须只标在该概念首次、最关键的出现位置。

3. **链路筛选**
   - 主 Agent 汇总 `linkage_inventory`，选择默认 3 到 5 条高价值链路深挖；项目很小时至少 2 条。
   - 优先选择直接承载主功能、跨模块最多、新手最难理解、Git 历史变化最多、失败路径最关键的链路。
   - 单纯工具函数、样式、普通 CRUD 和与核心 Happy Path 无关的边缘链路默认不深挖，只列为延伸阅读。

4. **第二层链路深挖**
   - 链路深挖 Subagent 池对每条入选链路并行产出独立页面素材，默认一条重点链路一个 Subagent。
   - Git 历史溯源 Subagent 对入选链路补充相关历史证据，无法验证时显式标注。
   - 图表 Subagent 可并行产出结构图、主流程图、链路图、数据流图或历史演进图素材。
   - 验证调试 Subagent 并行补齐每条链路的运行验证和观察点。
   - 主 Agent 检查每条链路是否达到链路深度标准；不达标时要求补证据或降级为低置信度说明。

5. **交叉对齐**
   - 对齐模块结构、调用链和历史证据。
   - 每个复杂设计都要说明当前职责和真实历史来源。
   - 冲突时优先使用代码、配置、调用链和 Git diff 证据。
   - 每个 Subagent 至少审阅另一个 Subagent 的关键结论；项目较大时启动交叉审阅 Subagent 池，并行指出缺证据、路径不一致、调用链断点、历史解释过度、代码摘录不足、验证命令不可执行或图表不一致的问题。
   - 主 Agent 建立证据矩阵，记录每个核心结论对应的文件、函数、配置、调用链或 Git 证据。

6. **教程大纲**
   - 先形成高证据密度大纲。
   - 汇总所有 Subagent 的 `page_count` 和页面清单，确定最终页面总数。
   - 大项目只展开最核心主流程和 3 到 5 条重点链路，其余模块列为延伸阅读。
   - 明确需要的架构图、调用链图或演进图。

7. **关键概念回填**
   - 主 Agent 或概念补充 Subagent 汇总所有页面素材中的 `concept_candidates`，按页面去重、合并同义词并筛掉过于基础、只需直译或与当前章节主线无关的词；最终保留与否由主 Agent 裁决。
   - 每页默认保留 3 到 5 个关键概念；超过时优先保留最影响理解入口、核心抽象、跨模块边界、分支异常或历史演进的概念。
   - 每个保留概念必须回填到对应详情页末尾的“关键概念补充”小节，不创建独立术语页，除非用户明确要求。
   - 正文中的 `[[concept:<id>]]` 预留下标必须转换为页内锚点下标，例如 `Adapter<sup><a href="#concept-adapter">1</a></sup>`。
   - 如果某个候选概念最终被筛掉，必须删除正文中的预留下标，不能留下空链接、断链或无解释下标。
   - 跨页重复出现的概念只在最核心、最早需要理解的页面解释一次；其他页面不重复解释，必要时用普通跨页链接指向已解释页面。

8. **HTML 生成**
   - 主 Agent 使用 `cosh-tutorial-html-docs` 创建或更新 `.cosh-docs/guide.html`。
   - 主 Agent 创建至少 6 个页面：1 个总览页，以及所有 Subagent 页面计划中列出的独立详情页。
   - 各详情页分别承载对应 Subagent 的结论，页面主题、证据、图表和阅读路径必须相互独立；不要把不同 Subagent 的内容混写进同一个正文页。
   - 总览页只负责项目定位、核心 Happy Path 摘要、重点链路清单、页面导航、最终页面清单和跨页面结论对齐，不替代任何独立详情页。
   - HTML 页使用小写英文短横线命名。
   - 图表资源放入 `.cosh-docs/asset/`，使用相对路径引用。
   - 每个 HTML 页面必须内联关键 CSS，不能只依赖 `.cosh-docs/asset/*.css` 外链；可保留外链 CSS 作为补充，但 `guide.html` 和所有详情页在外链 CSS 加载失败时仍应显示核心布局、卡片、标签、代码块、表格和步骤块样式。

9. **最终验收**
   - 核对证据矩阵、交叉质询结果和不可验证声明。
   - 核对每条重点链路是否有入口、终止点、逐步调用链、数据流、分支或异常路径、图表计划和证据清单。
   - 检查关键概念下标均有对应解释，筛掉的候选概念没有残留空下标。
   - 检查每张图是否满足图表质量要求。
   - 检查 `guide.html` 和所有详情页都包含内联 `<style>`，且不是只依赖外部 CSS。
   - 检查目录页入口、详情页链接、图片路径、移动端布局和离线可读性。
   - 向用户说明创建或修改的文件，并提示从 `.cosh-docs/guide.html` 开始阅读。

## 教程结构

默认输出至少 6 页结构，最终页数由 Subagent 调研后的页面计划决定。

### 30 分钟快速总览

总览页包含：

- 项目一句话定位。
- 技术栈与启动入口。
- 核心目录地图。
- 最重要的 1 条 Happy Path。
- 3 到 5 条重点执行链路清单，标明深挖优先级和对应页面。
- 2 到 3 个必须先理解的核心抽象。
- 当前最值得注意的复杂设计。
- 后续深入阅读路径。
- 指向所有独立详情页的入口，并标明每页来自哪个 Subagent 的页面计划。

### 独立详情页

至少创建五类互不混写的详情页；如果 Subagent 调研后建议拆分更多页面，按页面计划增加：

1. 结构分析页：项目全景、目录与模块职责、依赖方向、整体结构图。
2. Happy Path 总线页：启动或请求入口、核心 Happy Path、主调用骨架、关键代码证据、核心抽象。
3. 具体链路深挖页：每条链路一个页面，拆解入口、触发、逐步调用、数据流、分支、异常、终止点和证据。
4. Git 历史溯源页：主流程和重点链路相关 commit、tag、blame、diff、复杂设计的真实演进证据和不可验证声明。
5. 证据索引页：项目较大或链路页超过 5 页时创建，汇总核心结论到文件、函数、配置、调用链或 commit 的映射。

每个详情页都必须能独立阅读，具备自己的文件名、标题、摘要、目标问题、证据清单、正文、图表建议和延伸阅读。跨页引用可以存在，但不能让读者必须先读另一个详情页才能理解当前页面。

详情页不能只写摘要、结论列表或几段短说明。每页都必须围绕一个清晰的读者问题展开成完整讲解：先说明读者为什么需要理解这一页，再说明相关代码或历史证据在哪里，然后按顺序解释模块、链路、数据、分支和设计原因。除证据索引页外，每个详情页至少包含 4 个实质章节；每个实质章节至少包含 2 到 4 段解释性正文，必要时配关键代码、图表或文件路径。正文应解释“为什么这样走”和“读者应该看什么”，不能只复述图表或罗列文件名。

每个非总览详情页至少要包含一条“详细链路说明”或等价的连续执行/依赖/演进叙事：

- 结构分析页：说明一个入口如何穿过核心目录和模块边界，帮助读者把目录职责和真实调用关系连起来。
- Happy Path 总线页：从启动、请求、命令或任务入口开始，按阶段讲清主流程如何抵达核心能力和输出结果。
- 具体链路深挖页：按真实调用顺序逐步展开，不能跳过中间模块，也不能用“调用核心模块处理”替代代码节点。
- Git 历史溯源页：从当前复杂设计反推关键提交或阶段变化，说明哪些当前代码能从历史中验证，哪些不能。

### 运行验证与调试入口

初级开发工程师不应只靠阅读相信链路结论。每个 Happy Path 总线页和具体链路深挖页都必须提供“自己验证一下”内容；结构页和历史页按适用性提供。

运行验证内容必须包含：

- 最小启动或触发命令，例如测试命令、示例命令、CLI 调用、HTTP 请求、任务触发或脚本入口。
- 必要环境、配置、fixture、样例输入或前置数据；没有前置条件时明确写“无额外前置条件”。
- 预期可观察结果，例如终端输出、日志行、返回值、生成文件、状态变化、数据库记录或 UI 变化。
- 如何判断链路确实经过了本页说明的关键节点。
- 常见失败现象和第一检查点，例如缺依赖、环境变量缺失、配置文件路径错误、服务未启动、权限不足。
- 如果无法运行，必须说明原因，并提供静态验证替代方案，例如 grep 入口、查看测试、查看 fixture 或阅读调用方。

调试入口内容必须包含：

- 推荐断点或日志观察点，至少 2 个；每个观察点要有文件路径、函数或类名、触发方式和要观察的变量/状态。
- 最小输入如何触发断点。
- 断点命中后应看到什么，没命中时优先检查什么。
- 对不适合断点调试的项目，提供等价的日志、命令输出、测试断言或文件变化观察点。

### 关键概念补充

关键概念补充是为初级开发工程师降低阅读门槛的轻量机制，不是术语翻译页，也不是英汉词典。

每个 Subagent 在页面素材中可以预留正文下标，并输出候选概念：

```yaml
concept_candidates:
  - id: adapter
    term: Adapter
    page: runtime-startup.html
    source: src/runtime/adapter.ts
    first_context: 运行时初始化链路中首次出现
    why_explain: 这是理解运行时和外部实现隔离的关键抽象
    suggested_explanation: 在本项目里，它把外部实现包装成统一接口，让主流程不用关心底层差异。
```

正文素材中的预留下标使用稳定占位：

```text
Adapter[[concept:adapter]]
```

主 Agent 回填后，在正文中改为页内锚点下标：

```html
Adapter<sup><a href="#concept-adapter">1</a></sup>
```

详情页末尾增加“关键概念补充”小节，建议格式：

```html
<section id="concept-notes" class="card">
  <h2>关键概念补充</h2>
  <div id="concept-adapter">
    <h3>1. Adapter</h3>
    <p><strong>出现位置：</strong>src/runtime/adapter.ts</p>
    <p><strong>在本章节里：</strong>它把外部实现包装成统一接口。</p>
    <p><strong>为什么要懂：</strong>理解它之后，运行时初始化链路更容易串起来。</p>
  </div>
</section>
```

筛选规则：

- 每页默认最多保留 3 到 5 个概念。
- 只解释会影响理解当前章节主线的词。
- 不解释初级工程师默认应掌握的基础词。
- 不解释只靠直译就能懂、且在项目中没有特殊职责的普通词。
- 每个保留概念必须有 `source` 和 `why_explain`；没有证据路径或解释价值的候选必须删除。
- 被删除候选对应的正文 `[[concept:<id>]]` 占位也必须删除。
- 同一概念跨页出现时，只在最核心页面解释一次。

### 链路页固定结构

每个具体链路深挖页必须包含：

1. 这条链路解决什么问题。
2. 入口在哪里，什么条件触发。
3. 一条详细主链路说明：用连续叙事把入口、关键模块、跨模块跳转、数据变化、分支和终止点串起来，让读者不看源码也能先理解整体路径。
4. 一步一步经过哪些真实函数、类或模块。
5. 每一步为什么存在、读取或改写了什么数据、下一步为什么会发生。
6. 关键代码摘录：围绕入口、核心转发、关键分支、终止点各选 2 到 4 段短代码，说明每段代码在链路中的作用。
7. 数据在链路中如何变化，包括输入、中间态和输出。
8. 关键分支、异常路径和兜底行为。
9. 当前设计为什么这样，能否从 Git 历史验证。
10. 自己验证一下：最小触发命令、样例输入、预期输出和常见失败检查点。
11. 调试入口：推荐断点、日志观察点、要看的变量和没命中时的排查方向。
12. 读者下一步应该打开哪些文件继续读。

关键代码摘录不是完整源码复制。每段代码必须短小、可读，并配有文件路径、函数或类名、所在链路步骤、摘录目的和解释。优先摘录能证明调用关系、数据转换、分支条件、异常处理或终止行为的代码；不要摘录无关样板、样式、普通类型定义或大段重复实现。

链路页必须先写“详细链路说明”，再给步骤表或步骤块。详细链路说明不能少于 6 个连续步骤；每个步骤至少包含真实代码节点、当前输入、关键动作、输出或状态变化、下一跳依据和证据。项目本身不足 6 个节点时，要说明项目规模限制，并覆盖所有真实节点。

链路页素材建议使用以下结构：

```yaml
chain_name: 配置加载链路
entrypoint: src/index.ts -> main()
trigger: 程序启动时
terminal_point: 归一化配置交给运行时创建逻辑
detailed_flow:
  - order: 1
    node: src/index.ts -> main
    input: process.argv
    action: 解析 CLI 参数并取出配置路径
    output: config path
    next: loadConfig
    evidence: main 调用 loadConfig(args.config)
steps:
  - order: 1
    file: src/index.ts
    symbol: main
    action: 读取 CLI 参数
    next: loadConfig
    evidence: 函数调用
code_excerpts:
  - title: 入口函数读取 CLI 参数
    file: src/index.ts
    symbol: main
    step: 1
    purpose: 证明配置加载链路从启动入口开始
    excerpt: |
      const args = parseArgs(process.argv.slice(2));
      const config = await loadConfig(args.config);
    explanation: 这段代码把命令行参数转换成配置路径，并把控制权交给 loadConfig。
branch_points:
  - condition: 未找到配置文件
    behavior: 使用默认配置
failure_paths:
  - error: 配置解析失败
    handling: 抛出异常并终止启动
data_flow:
  - input: config path
  - intermediate: raw config
  - output: normalized config
verification:
  command: npm test -- config-loader
  prerequisites:
    - 已安装依赖
    - 使用仓库内测试 fixture
  sample_input: tests/fixtures/basic-config.json
  expected_observation: 测试通过，并能看到 normalized config 进入运行时创建逻辑
  fallback_static_check: rg "loadConfig" src tests
debug_points:
  - file: src/index.ts
    symbol: main
    trigger: 使用示例配置启动程序
    observe:
      - args.config
      - loadConfig 返回值
    if_not_hit: 检查启动命令是否走到正确入口
diagram_plan:
  type: sequenceDiagram
confidence: 高
unknowns: []
```

### 链路深度标准

每条入选深挖链路至少满足：

- 至少 5 个真实代码节点，除非项目本身不足 5 个节点。
- 至少 3 个真实文件路径，除非项目本身很小。
- 至少 1 条详细主链路说明，默认不少于 6 个连续步骤；项目本身不足 6 个节点时覆盖全部真实节点。
- 至少 1 个入口函数或类，以及 1 个终止点。
- 至少 1 个分支、异常路径或兜底逻辑。
- 至少 1 张调用链图、流程图或时序图。
- 至少 2 段关键代码摘录；复杂链路建议 3 到 5 段，覆盖入口、核心处理、关键分支或终止点。
- 至少 1 个运行验证方案，包含命令或触发方式、前置条件、样例输入、预期观察结果和失败检查点；无法运行时必须提供静态验证替代方案。
- 至少 2 个调试或观察点，包含路径、符号、触发方式和要观察的变量/状态；不适合断点调试时提供日志、测试断言或文件变化观察点。
- 每个关键步骤都有 evidence。
- 不允许只写“调用核心模块处理请求”“执行主流程”等无证据泛称。

## 证据要求

关键判断必须尽量引用：

- 文件路径。
- 函数名、类名、模块名。
- 调用链。
- 详细主链路说明，包含连续步骤、输入、动作、输出或状态变化、下一跳依据。
- 具体链路的入口、终止点、步骤、数据流和异常路径。
- 关键代码摘录，包含文件路径、函数或类名、摘录目的和解释。
- 运行验证命令、样例输入、预期输出、日志、测试断言或静态验证替代路径。
- 调试断点、日志观察点、变量状态和没命中时的排查方向。
- 配置项。
- commit hash、tag、blame 或 diff 摘要。
- README 或项目文档中的说明。

禁止用没有证据的空泛判断替代分析。历史演进只能基于真实 Git 证据；无法验证时写明“未能从历史验证”。

## 正确性保障

不能承诺生成内容绝对正确，但必须把错误风险显式压低并可复核。

每个 Subagent 输出时必须附带：

- `claims`：关键结论列表。
- `evidence`：每条结论对应的文件路径、函数名、配置项、命令输出、调用链、commit、tag、blame 或 diff。
- `detailed_flow`：详细链路或连续叙事步骤；链路页必须包含，结构页、Happy Path 页和历史页按主题提供等价的模块穿透、主流程或历史演进步骤。
- `code_excerpts`：关键代码摘录列表；链路页必须包含，其他页面按需包含。每段必须说明 file、symbol、purpose、excerpt 和 explanation。
- `verification`：运行验证素材；Happy Path 页和链路页必须包含 command 或 trigger、prerequisites、sample_input、expected_observation、failure_checks，无法运行时必须包含 fallback_static_check。
- `debug_points`：调试或观察点；Happy Path 页和链路页至少 2 个，包含 file、symbol、trigger、observe 和 if_not_hit。
- `confidence`：高 / 中 / 低，只允许基于证据强度判断。
- `unknowns`：未能验证的点、缺失历史、无法运行的命令或范围限制。
- `concept_candidates`：本 Subagent 页面中预留的关键概念候选，必须包含 id、term、page、source、why_explain 和 suggested_explanation；没有候选时返回空列表。
- `review_notes`：自己认为最需要主 Agent 或其他 Subagent 复查的点。

主 Agent 必须执行：

1. **证据矩阵**：为所有页面中的核心判断建立“结论 -> 证据 -> 页面位置”的映射。没有证据的判断不得写成确定语气。
2. **交叉质询**：让结构、链路、历史三类结论互相校验；例如目录职责必须能解释调用链，历史叙事必须能对应当前代码。
3. **冲突处理**：遇到 Subagent 结论冲突时，按代码 > 配置 > 测试 > 文档 > Git 历史解释的顺序裁决；无法裁决时在页面中标注争议和原因。
4. **可复核引用**：每个详情页至少包含一个证据清单，列出读者可以直接打开的路径、函数、配置或 commit。
5. **链路完整性检查**：每条重点链路必须能从入口连续追到终止点；中断处必须写明断点原因、推断依据和置信度。
6. **概念回填检查**：筛选 `concept_candidates`，将保留概念回填到对应详情页末尾，清理未保留概念的正文占位，并确保所有下标都能跳转到本页或明确的跨页解释。
7. **风险声明**：总览页必须说明本次分析的置信边界，例如未运行测试、Git 历史不足、入口不唯一、生成图为抽象图而非完整实现图。

如果项目可以运行测试、静态检查或示例命令，主 Agent 应优先运行与主流程相关的低风险命令；无法运行时必须写明原因，不得假装验证通过。

## 质量闸门与返工规则

质量闸门用于阻止低证据、短摘要、断链路或不可复核的内容进入最终 HTML。主 Agent 在生成 HTML 前必须执行一次闸门检查；生成 HTML 后必须再执行一次页面级闸门检查。

### 阻断项

出现以下任一情况时，不得直接生成或交付最终页面，必须先返工：

- 缺少实际 Subagent 输出，或 Subagent 输出不是结构化素材。
- 任一重点链路缺少 `detailed_flow`、`code_excerpts`、`branch_points`、`failure_paths`、`data_flow` 或 evidence。
- Happy Path 页或重点链路页缺少 `verification` 或 `debug_points`，且没有说明无法运行或无法断点调试的原因。
- 重点链路没有入口、终止点、连续步骤，或中间步骤用“调用核心模块处理”这类泛称替代真实代码节点。
- 关键代码摘录没有文件路径、函数或类名、用途说明和正文解释。
- 页面只有摘要、结论列表或短段落，不能独立回答该页目标问题。
- 历史演进结论没有 commit、tag、blame 或 diff 证据，却被写成确定事实。
- 图表节点或边无法对应代码、配置、调用链或 Git 证据。
- 概念下标没有对应解释，或被筛掉的概念仍残留 `[[concept:<id>]]` 占位。
- 任一 HTML 页面只依赖外部 CSS，缺少可独立渲染核心布局的内联 `<style>`。
- `.cosh-docs/guide.html` 无法进入所有详情页，或详情页链接、图片、图表路径错误。

### 返工流程

1. 主 Agent 为每个阻断项写出具体返工请求，包含页面名、缺失字段、相关链路、应补充的证据类型和最低完成标准。
2. 将返工请求交回对应 Subagent；结构问题交给结构分析 Subagent，链路问题交给链路发现或链路深挖 Subagent，历史问题交给 Git 历史溯源 Subagent。
3. Subagent 必须返回更新后的结构化素材，而不是只回复解释性文字。
4. 主 Agent 重新执行证据矩阵、链路完整性、概念回填和图表一致性检查。
5. 同一问题最多返工两轮；两轮后仍无法补齐时，主 Agent 必须降级或移除相关内容。

### 降级规则

返工后仍缺证据时，不得用确定语气硬写。主 Agent 必须按以下方式处理：

- 核心链路缺少关键节点：优先更换为证据更完整的链路；不能更换时标为低置信度，并写明断点原因。
- 历史证据不足：保留当前代码解释，删除确定性历史叙事，改写为“未能从历史验证”。
- 代码摘录不足：补充可复核路径；如果项目代码本身过小或抽象层过薄，说明规模限制。
- 运行验证不可用：说明不可用原因，改为静态验证路径；不得假装命令已通过。
- 调试断点不可用：改为日志、测试断言、命令输出或文件变化观察点。
- 图表证据不足：标注为“概念图”或“推断图”，不得标为实现事实。
- 页面内容密度不足：合并到更相关页面或要求补写；不得以短摘要独立成页。

### 闸门记录

最终交付前，主 Agent 必须在总览页或风险声明中简要记录：

- 哪些检查已通过。
- 哪些测试、命令或历史证据无法运行或无法获取。
- 哪些页面、链路或历史解释被降级为低置信度。
- 是否发生返工，以及返工后仍保留的已知缺口。

## 图表质量要求

原理图是教程的一等产物，不是装饰图。每个 Subagent 在页面计划里必须给出图表计划：图表数量、图表类型、表达的问题、节点清单、边或数据流、证据来源和推荐放置页面。

优先使用可维护的文本图表或代码生成图表：

- 架构和模块关系：Mermaid `flowchart` 或 `C4` 风格分层图。
- 调用链和时序：Mermaid `sequenceDiagram` 或从入口到关键函数的分层流程图。
- 具体链路深挖：优先用 Mermaid `sequenceDiagram` 或带泳道的流程图，节点必须是实际文件、函数、类、配置或外部边界。
- Git 演进：Mermaid `timeline`、提交时间线或按阶段的 diff 摘要图。
- 复杂状态或流程：状态图、泳道图或阶段图。

每张图必须满足：

- 只表达一个核心问题，不把目录树、调用链和历史演进塞进同一张图。
- 节点名称使用真实模块、函数、配置或 commit 的短名，避免“核心模块”“处理器”这类无证据泛称。
- 每条关键边都能追溯到 import、调用、配置引用、数据流、命令入口或 Git diff。
- 图下方有 1 到 3 句解读，说明读者应该看什么，不重复图中所有文字。
- 大图必须分层或拆图；单图建议不超过 12 个主要节点，超过时拆成总览图和局部图。
- 图中文字在移动端不应拥挤；复杂图可横向滚动，但不能被截断到无法阅读。

主 Agent 生成 HTML 后必须验收：

- 图表文件或内联图能离线渲染。
- 图表链接、图片路径和相对路径正确。
- 图表与正文结论一致，没有出现正文没有解释的节点或边。
- 图表视觉层级清楚，入口、核心路径、外部依赖、历史阶段有明显区分。
- 对无法从代码或 Git 证据确认的图，标注为“推断图”或“概念图”，不得标为实现事实。

## 范围边界

应做：

- 项目结构解读。
- 主流程代码走读。
- 重点执行链路深挖。
- 核心抽象解释。
- 真实 Git 演进分析。
- `.cosh-docs/` HTML 教程站点生成。

不应做：

- 全量 API 文档生成。
- 所有文件逐个解释。
- 没有筛选优先级地展开所有链路。
- 架构优劣评审。
- 代码修改方案。
- 性能优化方案。
- 没有证据的历史故事化推演。

## 质量检查

交付前确认：

- 已实际使用 Subagent 能力并由主 Agent 汇总监督。
- 各 Subagent 都已输出页面计划，包括建议页面个数和每页内容范围。
- 各 Subagent 都已输出 claims、evidence、detailed_flow、code_excerpts、verification、debug_points、confidence、unknowns、concept_candidates 和 review_notes。
- 已建立 `linkage_inventory`，并筛选 3 到 5 条高价值链路；项目很小时至少 2 条。
- 主 Agent 已完成证据矩阵、交叉质询和冲突处理。
- 主 Agent 已执行质量闸门；阻断项已返工、移除或降级，并在风险声明中记录。
- 主 Agent 已完成关键概念回填：保留概念有解释，筛掉概念无残留下标，每页概念数量不过载。
- 已使用 `cosh-tutorial-html-docs` 创建或更新 HTML 教程。
- `.cosh-docs/guide.html` 存在并包含教程入口。
- `guide.html` 和所有详情页都包含内联 `<style>`，外部 CSS 只作为补充，不是唯一样式来源。
- 总览页和所有 Subagent 页面计划中的独立详情页均可从目录页进入。
- 详情页分别对应结构分析、Happy Path 总线、具体链路深挖、Git 历史溯源的页面计划，没有被合并成单页正文。
- 每个详情页都有足够内容密度：不是摘要列表，至少包含一个详细链路、模块穿透或历史演进叙事，能回答本页目标问题。
- 每条重点链路都有独立页面，且包含入口、终止点、步骤、数据流、分支或异常路径、图表计划和证据清单。
- 每条重点链路都有详细主链路说明，步骤连续、节点真实、数据变化清楚，没有跳过关键中间模块。
- 每条重点链路都有关键代码摘录，摘录能支撑正文判断，并且每段都有路径、符号、用途和解释。
- Happy Path 页和重点链路页都有运行验证方案、预期观察结果、常见失败检查点和调试或观察点；无法运行时有静态验证替代方案。
- 每个详情页都有证据清单和必要的置信边界说明。
- 每张原理图都有图表计划、证据来源、正文解读和渲染验收。
- 图表和图片资源路径正确。
- 页面可离线打开，不依赖后端服务或联网资源。
- 关键判断有文件、调用链或 Git 历史证据。
- 大项目没有失焦为全仓库百科，主线仍围绕核心 Happy Path。
